## 一、亮点：一次为 AI 初版代码做的性能 code review

### 1.0 一句话版本

**首页功能跑通之后，我发现 AI 生成的初版代码在体验和性能上是「能用但不耐看」。于是我做了一轮 code review，把三个具体的体感问题定位成三条技术原因，再逐条优化——首屏慢是图片没走缓存，快滑看到骨架屏是预加载触发太晚，滑久了卡顿是列表节点在无限增长。**

这个项目的亮点不在"我写了多少功能"，而在**我能看出 AI 产出的代码哪里不对，并且知道怎么改**。

### 1.1 现象一：首屏渲染时间长

**根因**：初版把所有图片都当成「实时数据」处理——每次冷启动都要重新拉一遍开屏广告和海报，且图片本身没有走 CDN，体积大、节点远。首屏要等这些大文件下载完才敢撤开屏，加上列表接口串行在后，首屏被图片下载吃掉了大量时间。

**优化**：CDN + imageCache 两级缓存，并且**命中本地缓存后跳过对应接口请求**。

1. **资源上 CDN**：把开屏广告、海报等非本地图片统一走 CDN 域名，冷启动时从就近边缘节点取，降低首字节时间。
2. **本地文件缓存**：用 `wx.getFileSystemManager().saveFile` 把图片持久化到本地，缓存键值存成 `{ localPath, src }`——`src` 是这次缓存对应的后端资源 URL。
3. **命中即跳过接口**：启动时先读本地缓存记录，版本没过期就直接用本地文件渲染，**不再发起 `/info/banner`、`/info/openad` 这类图片资源请求**。图片资源的请求直接消失，首屏少了一整轮 RTT。
4. **失效与兜底**：后端换图后 URL 变化，本地 `src` 比对不通过就重新请求并重下；再用 `access` 校验本地文件是否被系统回收，文件不在了同样降级回接口请求。

**这一步的关键认识**：缓存的价值不只是"省一次下载"，而是**能把接口请求整段跳过**。前提是本地必须存一个可比较的版本标识（URL 里的版本号或内容 hash），否则就会一直读到旧图。

### 1.2 现象二：滑动很快的时候，下方的帖子是骨架屏

**根因**：初版是"滚到底才开始请求下一页"，请求的 RTT 期间用户已经滚到空白区域，于是看到骨架屏。这不是渲染问题，是**预加载时机**问题——数据就绪时间落后于用户滚动速度。

**优化**：预加载 + 后端分页。

1. **后端分页**：接口按 `page` 返回，单页控制在约 20 条，首屏 payload 不再随数据量增长。
2. **阈值预加载**：不等滚到底，在**距离底部还有一段距离时**就发起下一页请求，让数据在用户滚到之前就绪。快照里的阈值是 `scrollHeight - scrollTop < 3000`（约一屏半）。
3. **防重入与终止**：用 `is_loading_more` 锁住并发，用 `is_last` 终止到底后的无意义请求，避免快速滚动时连发重复请求。
4. **骨架屏收敛**：骨架屏只在"真正的首屏空窗"出现，不再作为翻页常态。

**这一步的关键认识**：分页解决的是"单次传输量"，预加载解决的是"用户滚到之前数据有没有到"。**只做分页不做预加载，快滑一样会看到骨架屏。**

### 1.3 现象三：滑动久了之后卡顿

**根因**：初版用 `wx:for` 全量渲染整个列表，分页又是不断 `concat` 追加——**滚动越久，真实渲染的节点数线性增长**，每次 `setData` 的 diff 范围和样式重算成本随之上升，几百条之后滚动明显掉帧。

**优化**：改用微信官方推荐的长列表组件，只渲染可视区，滚出去的节点回收复用。

1. **可视区渲染**：列表组件负责计算当前可视区间，只挂载区间内的帖子卡片，上下用撑高的占位块维持滚动条长度。
2. **节点回收复用**：滚出可视区的卡片被回收后再复用到新进入的卡片上，**DOM 数量与列表长度解耦**，从"O(列表长度)"变成"O(可视区)"。
3. **复用正确性**：复用单元的 key 必须用稳定的业务 ID（帖子 ID），不能用 `index`，否则复用错位会把上一个卡片的内容显示到新位置。
4. **图片配合**：卡片进入可视区才触发图片加载，移出后保留占位，避免滚动过程中反复请求造成抖动。

**这一步的关键认识**：长列表的性能瓶颈不是"数据多"，而是"**挂载的节点多**"。虚拟化的本质是把「数据长度」和「渲染节点数」解耦。

### 1.4 三条追问防线

| 会被问 | 怎么答 |
|---|---|
| 你怎么知道缓存过期了？ | 本地存了资源 URL 作为版本标识，URL 变了就是过期。低频变化的资源才允许跳过接口，列表这类实时数据不跳 |
| 阈值 3000 怎么定的？ | 按"一屏高度 + 网络 RTT 对应的滚动距离"估。太大浪费流量，太小来不及，这个值是压测后调的 |
| 快速滚动连续触发怎么办？ | `is_loading_more` 锁住并发请求，`is_last` 终止到底后的请求，保证同一时刻只有一个分页请求在飞 |
| 滚动速度极快，预加载也追不上怎么办？ | 这种极端场景下骨架屏是合理兜底——宁可让用户看到占位，也不要白屏或卡住主线程 |
| 长列表组件的高度怎么处理？ | 定高最稳；不定高要先测量建高度缓存再算区间。这块是组件本身的主要约束 |
| 用了 index 做 key 会怎样？ | 复用错位，节点被回收后复用到新位置时会带上旧内容，表现为卡片内容闪烁或串位 |

> ⚠️ **"微信官方推荐的长列表组件"需要确认具体是哪一个**，因为两者的追问方向完全不同：
> - **`recycle-view`**（微信官方开源的长列表组件）：WebView 渲染下可用，用"屏数 × 每屏条数"维护可视区并提供回收上下文，追问会落在高度测量与回收配置上；

> 定下来之后，这一节的细节我再按实际那个写实。

## 二、做项目时有什么难点？

### 2.1 难点一：AI 产出的代码「功能对、体验不对」，怎么把它识别出来

这是这个项目里最本质的难点。AI 生成代码的默认目标是"功能跑通"——接口调通了、数据渲染出来了，它就认为任务完成了。但**首屏关键路径有多长、列表规模会增长到什么量级、预加载该在什么时机触发，这些它默认不会主动考虑**。

我建立的做法是：功能跑通之后，必须补一轮**体验走查**，而不是直接交付。走查方式是三条——

1. 真机走查，不看模拟器，因为滚动掉帧这类问题只有真机能复现；
2. 看性能面板的首屏分段耗时，确认时间花在"资源下载"还是"接口等待"上；
3. 长列表压测，连续滚动到几百条，看掉帧出现在什么位置。

**更重要的沉淀**：把 review 出来的问题反向补进给 AI 的约束里，形成可复用的规则——长列表必须虚拟化、图片必须走缓存并做版本校验、分页必须带预加载阈值、复用 key 必须用业务 ID。这样下一次生成就不会再犯同样的错。

> 这一段和简历里「探索 openspec、个人 skills 等 harness engineering 实践」是同一件事的两面，可以互相印证着讲。

### 2.2 难点二：预加载时机是"请求 RTT"与"用户滚动速度"的赛跑

骨架屏问题的难点不在实现，而在**阈值取舍**：阈值太保守，快滑还是会看到骨架；阈值太激进，用户慢慢看的时候会白白拉一堆用不上的数据，浪费流量也增加服务端压力。

而且快速滚动会连续触发滚动事件，如果不在请求层做防重入，会出现同一个 `page` 被重复请求、回来的顺序还可能错乱。所以最终是"阈值 + 请求锁 + 终止标记"三件套一起上才稳。

### 2.3 难点三：缓存和「后端上了新素材」的冲突

缓存最容易踩的坑是**用户一直看到旧图**——后端换了新海报，但本地缓存还命中，前端就永远显示旧的。

初版的思路是"按 key 缓存"，key 不变就永远命中，这个问题无解。后来改成**把源 URL 一起存进缓存记录**：URL 里带版本或 hash，后端换图 URL 就变，本地比对不通过，缓存自动失效并重新下载。等于用资源地址本身当版本号。

### 2.4 难点四：长列表的「复用正确性」

虚拟化之后，节点是复用的，这带来一个很容易忽略的问题：**复用单元的 key 如果不稳定，节点被回收再复用到新位置时，会带着上一个卡片的内容出现**，表现为滚动时卡片闪一下或内容串位。所以 key 必须用帖子 ID 这类稳定业务标识，不能用 `index`。这类问题不会报错，只会"看起来有点怪"，排查成本很高。

### 2.5 ⬜ 难点五：工程化实现——埋点与监控（设计态）

> **先说边界**：项目当前**没有埋点与监控**——前端全文没有任何上报调用，`IntersectionObserver` 一次都没用过，也没有任何独立的上报域名或上报接口。
> 所以这一节讲的是**方案**。面试时按「如果我来做，我会这么设计」的口径讲，别讲成已上线。

#### 为什么这也是难点

埋点难在它不是「加个接口」，而是三件事必须同时对：**口径要先定**、**不能拖累主流程**、**它自己还得可观测**（埋点挂了前端不会报错，只会数据静默消失）。

下面按「口径 → 选型 → 实现」三步讲。

#### 第一步：口径——我们要的是「有效曝光」

「帖子浏览量」这个词很模糊：「多少人次刷到」和「多少人次真的看到」是两个数。我们取后者——

> **有效曝光 = 卡片在可视区内露出 ≥ 50% 的面积，且连续停留 ≥ 1 秒，记一次。**

这个口径不是我拍的，它是广告行业通行的可视曝光标准（MRC / IAB：50% 像素 + 连续 1 秒；神策的曝光采集用的也是「可见比例 + 有效停留时长」这套）。两个细节必须说清：

- **「连续」停留**：露出过半才计时，中途滑出去就停止并清零，再滑回来重新计时——**不是累加**。
- **同一次页面停留内只记一次**：同一张卡上下滑动来回蹭到只算一次；离开页面再回来算新的一次。

为什么不直接用「进可视区就算一次」的 PV？因为那样滑得越快涨得越快，数字就失去意义了。我们展示它是当热度信号用的，希望它对应「真的被人看到了」。

#### 第二步：选型——不接商业 SDK，写个 40 行的轻量自研

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 神策 `sa-sdk-miniprogram`（开源）、GrowingIO | 能力最全（全埋点、曝光插件、现成看板），但我们只要曝光这一类事件，为它引一个 SDK、还要把数据过第三方，不划算 |
| 微信官方 `wx.reportAnalytics` | 零成本，但数据只进微信后台，自己查不到，做不了聚合 |
| **自研轻量 tracker** | 只要一个文件、两个方法；事件、口径、上报链路全在自己手里 |

上报另起一个域名（比如 `log.tripleuni.com`）。它的价值**不是「绕过并发限制」**（小程序的并发上限是**全局 10 个、不分域名**），而是**服务端解耦**：埋点流量直接落到独立服务/日志，不经过业务应用，业务接口不会被埋点的洪峰影响，埋点服务还能单独扩容、单独降级。

> ⚠️ 运维上有个前置动作：新域名要加进小程序后台的**服务器域名白名单**，且白名单的修改次数是有限制的（以当前后台规则为准），所以域名要在动手写代码之前先定下来。

> ⚠️ **比域名重要得多的一件事**：埋点请求会**挤占那 10 个全局并发名额**。腾讯课堂小程序出过真实的线上事故——第三方上报服务异常，上报请求一直 pending，把并发打满之后业务请求直接被阻塞，iOS 上表现为明显卡顿，最后专门做了个请求排队模块（并发超过阈值时延后发送低优先级请求）。
> 所以上报这边有三条纪律：**设短 timeout**（2~3 秒，别占着名额不放）、**失败即丢**、并发紧张时给业务让路。

#### 第三步：实现——一个 40 行的 tracker

```javascript
// utils/tracker.js —— 有效曝光采集 + 批量上报
const queue = []
let seq = 0
const timers = {}                                    // post_id -> 停留计时器
const session = `${Date.now().toString(36)}${Math.random().toString(36).slice(2, 6)}`   // ⑤ 冷启动生成一次

// 曝光：露出过半才开始计时，连续满 1 秒才算一次
export function watchExposure(ctx, selector) {
  ctx.createIntersectionObserver({ thresholds: [0.5] })
    .relativeToViewport()
    .observe(selector, (res) => {
      const id = res.dataset.id                       // ① 后端返回的帖子 ID
      if (res.intersectionRatio >= 0.5) {
        if (timers[id]) return                        // ② 本页已计过，不重复
        timers[id] = setTimeout(() => {
          track('post_exposure', { post_id: id })      // ③ 满 1 秒才入队
        }, 1000)
      } else {
        clearTimeout(timers[id]); delete timers[id]    // ④ 滑出去就清零重来
      }
    })
}

function track(event, props) {
  queue.push({
    event_id: `${session}-${++seq}`,                   // ⑤ 客户端生成，重传不变
    event, ts: Date.now(), ...props,
  })
  if (queue.length >= 6) flush()
}

export function flush() {
  if (!queue.length) return
  const batch = queue.splice(0)                        // ⑥ 先出队再发，失败即丢
  wx.request({
    url: `${report_url}/log`, method: 'POST', data: batch,
    timeout: 3000,                                     // ⑦ 短超时，别占着并发名额
    fail: () => {},
  })
}

setInterval(flush, 5000)                               // ⑧ 定时兜底
wx.onAppHide(() => flush())                            // ⑨ 切后台兜底
```

对着这段代码，有五个点值得展开：

**① 业务 ID 就是后端返回的帖子 ID。** 列表接口本来就返回了 `uni_post_id`，wxml 上挂成 `data-id="{{item.uni_post_id}}"`，观察器回调里的 `dataset.id` 直接拿来上报——**不需要前端自己造 ID**。

要点是「必须走 `dataset`，不能按节点位置认卡片」：我们列表是虚拟化的，节点会被回收复用，按「第几个节点」认卡片的话，复用之后 A 卡的观察器会把 B 的曝光记到 A 头上。这类错位不报错，只会让数据静默失真。

**上报带哪个用户标识？不能带 `user_serial`。** 它是个用户自己设置、还能随时改的社交 ID（[userdata.js](../../../../../tripleuni-frontend-wechat/pages/userdata/userdata.js#L79-L96) 里校验完就调 `/user/profile/update`），改一次同一个人就被拆成两个，行为链路直接断。而微信侧的 `openid` 前端又拿不到——`wx.login()` 只给一个临时 `code`，得由后端带 appid + secret 去换（[app.js](../../../../../tripleuni-frontend-wechat/app.js#L406-L418)）。
所以上报走**双标识**：客户端生成一个持久化的匿名 ID（存 storage）随事件上报，同时带上 token，后端凭 token 反查真实用户、再做「匿名 ID → 用户」的关联。这就是神策 SDK 里 `anonymous_id` + `login_id` 的模型，好处是**登录前的浏览也能在登录后归到同一个人身上**——「刷了几条才注册」这类分析全靠它。

**②④ 去重的两层含义。** `timers` 里已经有这个 ID 就说明本页已计过，直接 return（同页去重）；滑出去走 `clearTimeout` 清零，所以「连续 1 秒」是真的连续，**不是把几次停留加起来**。跨页面、跨天的去重不在这里做，放到后端按「用户 × 帖子 × 天」聚合。

**⑤ `event_id` 解决的是另一个问题：重传导致的重复。** 批量上报 + 超时重试会让同一条事件到后端两次（客户端以为超时了、其实服务端已经收到），这类重复靠业务字段去不掉。生成上想清楚三点就行：

- **别用 UUID v4。** 它是 36 个字符，每天百万级事件白白多传好几 MB；而且小程序里没有 `crypto.randomUUID()`，官方的 `wx.getRandomValues()` 是**异步**的——为了拿个随机数把 `track` 变成异步，得不偿失。
- **「会话前缀 + 会话内自增」就够。** `session` 冷启动生成一次（时间戳 36 进制 + 几个随机字符），`seq` 内存自增，拼出来 15 个字符以内。它天然满足两件事：**同一会话内不会重号**（`seq` 保证），**跨会话不会重号**（`session` 变了）——所以就算上一轮的数据还在本地队列里等着补传，重启后新生成的 ID 也不会和它撞。
- **要是把事件落 storage 做失败暂存，`event_id` 必须跟着一起存。** 重传的必须是**同一个** ID，重新生成一遍等于没去重。
- 还有更省事的替代：如果事件本身就有天然唯一键，**直接拿业务键当 `event_id`**——我们的口径就是「用户 × 帖子 × 天」去重，那 `user_serial:post_id:日期` 这个组合本身就是幂等键，连随机数都不用。

服务端拿到它，建唯一索引（`INSERT IGNORE`）或者 `SET event_id 1 NX EX 86400` 就能把重复挡掉。但别和 ② 混：一个去「传输层重复」，一个去「业务层重复」，互相替代不了。

**⑥⑦⑧⑨ 批量上报、短超时、两处兜底。** 单条一发会被曝光量打爆（一屏 3 条 × 每次启动），所以攒批：满 6 条或每 5 秒 flush 一次，切后台再兜一次。这两个数字参考了成熟 SDK 的默认值（神策小程序 SDK 是 6 条 / 6 秒，神策 App SDK 是 100 条 / 15 秒，Segment 是 15 条 / 10 秒）——**我们这种体量取小不取大**，否则光靠「满 N 条」触发，可能几分钟都发不出去。

两个细节：

- `queue.splice(0)` 放在请求之前，是为了**失败即丢**：浏览量的数据丢一点可以接受；反过来「先发再出队」会让失败重试和下一批混在一起，去重逻辑立刻变复杂。
- `timeout: 3000` 是给并发让路。`wx.request` 的并发上限是全局 10 个，一个卡住的上报请求就是占着一条车道不放；而默认超时是 60 秒，对埋点来说太长了。

`onAppHide` 那条也要留意——微信官方《小程序运行机制》写明，切后台约 5 秒后 JS 线程会被停止、**回调要等回前台才触发**，所以这里只 flush、不做任何依赖回调的后续逻辑。

**最后一个约定：上报和展示解耦。** 前端上报的是**事件**，不是数值；前端**绝不做本地 `+1`**——那会重复计数、刷新跳变、和后端对不上。代价是自己刚看过的内容不会立刻 +1（后端聚合是分钟级的），这个延迟我们接受。

#### 补充：上报时机的生命周期映射

上报的时机只判断一件事：**事件确实发生了，数据也拿得到，才上报。**

页面生命周期里，`onLoad` / `onReady` 只触发一次，`onShow` / `onHide` 每次都触发。所以「用户又来看了一次」这类 PV 不能用 `onLoad`。页面「不见」有四种来源：跳新页面、切 tab、进后台只走 `onHide`，页面销毁才走 `onUnload`，没有哪条生命周期能单独表示「用户离开了」。

| 事件 | 挂在哪 | 为什么 |
|---|---|---|
| 启动 `app_launch`、冷/热启动区分 | `App.onLaunch` + `App.onShow` | onLaunch 全局一次且能拿 `scene`/`query`；onShow 冷热都触发 |
| 页面 PV | `Page.onShow` | `onLoad` 只一次，切 tab、返回都会漏 |
| 停留时长 | `onShow` 记 t0，`onHide` / `onUnload` 记 t1 | 两条出口都要挂 |
| 首屏可见 | 首批 `setData` 回调 | `onReady` 时首屏数据往往还没回来 |
| 元素曝光 | `onReady` 后 `createIntersectionObserver` | 生命周期表达不了「露出 50% 且停留 1 秒」 |
| 点击 | WXML `bindtap` + `data-*` | 交互归事件 |
| 组件行为 | 组件 `attached` / `ready` | `attached` 时 `properties` 已就绪 |
| 组件内曝光 | 组件 `pageLifetimes.show` / `hide` | 组件不感知宿主页面显隐 |
| 异常 | `App.onError` / `App.onUnhandledRejection` | 兜住脚本错误和未处理的 Promise |
| 兜底 flush | `App.onHide` | 切后台约 5 秒后逻辑层被挂起 |

有两处容易搞反：

- `onShow` 不一定跟在 `onLoad` 后面。首次进入是 `onLoad → onShow → onReady`，从别的页面返回时只有 `onShow`。所以 `track()` 只写在 `onLoad` 里，PV 会偏低。
- `onHide` 是「可能还会回来」，`onUnload` 是「再也不会回来」。停留时长按前者配对，页面级定时器按后者清理。

项目里有个现成的例子：[app.js](../../../../../tripleuni-frontend-wechat/app.js#L1401-L1421) 在末尾重写了全局 `Page` 构造器，给每个页面的 `onShow` 前置注入主题更新：

```javascript
const page = Page
Page = function (pageData) {
  _handleInstanceMethod(pageData, 'onShow', function () {
    getApp().updateTheme(false)
  })
  page(pageData)
}
```

埋点 SDK 做全局 PV 是同一个做法，把 `updateTheme` 换成 `track('pv')` 就行。两点注意：页面没定义 `onShow` 时要补上（`_handleInstanceMethod` 的 `else` 分支），这段代码得放在所有页面模块加载之前，所以在 `app.js` 末尾。组件同理，把 `Component` 也代理一层。

截屏记录 [app.js](../../../../../tripleuni-frontend-wechat/app.js#L298-L323) 是另一种：用 `wx.onUserCaptureScreen` 监听，注册时机放在 `launch()` 成功之后。监听器本身不是生命周期，但上报要带 token，得等登录态确认。

| 会被问 | 怎么答 |
|---|---|
| PV 为什么不用 `onLoad`？ | 一个页面只触发一次。切 tab、从后台回来、从详情页返回都只有 `onShow`，用 `onLoad` 会漏计 |
| 停留时长挂 `onUnload` 够吗？ | 不够。切 tab 和跳新页面只走 `onHide`，会丢掉大部分场景 |
| 曝光为什么不放生命周期里做？ | 生命周期描述的是整个页面，表达不了「某个元素露出一半并停留 1 秒」，只能靠 `IntersectionObserver` |
| 组件埋点挂 `attached` 还是 `ready`？ | 只上报属性用 `attached`；要读节点位置和尺寸用 `ready` |
| 上报什么时候 flush？ | 满 N 条或定时触发，`App.onHide` 兜底。但切后台约 5 秒后逻辑层被挂起，兜底不绝对可靠 |

#### 顺带两句：监控与防刷

- **埋点自己也要被监控**——看上报成功率、队列丢弃量就够。埋点挂了前端不会报错，只会数据静默消失，这是最典型的沉默故障。
- **量级要提前估**：曝光是最容易爆量的埋点（一屏 3 条 × 每次启动 × 全部用户 = 每天百万级），所以客户端先做去重和采样，上报走独立服务承载。
- **防刷**：校园社区里「刷热度」是真实动机，所以**对外展示的数字**建议用按「用户 × 帖子 × 天」去重后的 UV，底层照旧收 PV 用于分析，并对异常流速设告警（单用户 1 分钟曝光 500 次就该报警）。

#### 口述话术

> 「埋点这块我的判断是：难点不在写上报接口，在口径和链路。
>
> 我拿『帖子浏览量』举例。第一步是定口径——『多少人次刷到』和『多少人次真的看到』是两个数，我们取后者，也就是**露出过半 + 连续停留 1 秒**记一次，这个口径就是广告行业通行的可视曝光标准。第二步是选型：我们只要曝光这一类事件，所以没接神策那种完整 SDK，自研了一个 40 行的 tracker。
>
> 实现上有几个点。曝光用 `IntersectionObserver`，业务 ID 直接取后端返回的帖子 ID 挂在 `data-id` 上——不能按「第几个节点」认卡片，因为列表虚拟化之后节点会回收复用，复用错位会把曝光记到别人头上。去重分两层：同一次页面停留内只记一次，跨天的交给后端按『用户 × 帖子 × 天』做。
>
> 上报是攒批的，满 6 条或 5 秒发一批、切后台再兜一次，参数参考神策和 Segment 的默认值往下调。这里有个容易被忽略的点：小程序的 `wx.request` 并发上限是**全局 10 个、不分域名**，所以上报请求我给的是 3 秒短超时、失败即丢——腾讯课堂就出过上报服务把并发占满、业务请求被阻塞、iOS 明显卡顿的事故。独立域名解决的是服务端隔离，不是并发。
>
> 每条事件带一个客户端生成的 `event_id` 防重传重复，用的是「会话前缀 + 会话内自增」，十几个字符。不用 UUID，也不用 `wx.getRandomValues()`——小程序里没有 `crypto.randomUUID()`，而它是异步的，为了拿随机数把上报变成异步不划算。这个 `event_id` 和前面说的『同一张卡重复曝光』是两种去重，不能混。最后前端只上报事件、不做本地自增，浏览量是后端聚合出来的。」

## 三、你是怎么优化首屏加载时间的？怎么记录的？

### 3.1 已落地的优化

优化内容见第一部分 1.1 与 1.2，这里只列清单便于口述时快速对答：

| 手段 | 解决的问题 |
|---|---|
| 资源上 CDN | 图片下载链路长、首字节慢 |
| imageCache 本地文件缓存 | 冷启动重复下载大图 |
| 缓存命中跳过图片资源接口 | 首屏少一整轮 RTT |
| URL 版本比对 | 缓存与后端数据不同步 |
| 后端分页（约 20 条/页） | 首屏 payload 随数据量增长 |
| 阈值预加载 | 快滑时数据未就绪 |
| 请求锁 + 终止标记 | 快速滚动重复请求 |
| 长列表虚拟化 | 节点数随滚动线性增长 |
| 开屏四路并发 + 计数收口 | 开屏等待策略 |
| 按需注入 / 骨架屏 | 首屏白屏与无用组件注入 |

### 3.2 首屏的最大瓶颈（主动抛出，加分项）

首屏的四个数据请求实际上被登录校验串住了：页面要等 `/user/check/wechat` 返回、`token_checked` 置位之后才发起 `initializeWhenReady`。所以真正的关键路径是**「登录校验 → 数据请求 → 渲染」**，图片缓存只是减少了最后一步的等待。

**可以提的下一步**：让校验与数据请求并行，无 token 时走游客态兜底，直接把这段串行砍掉。

### 3.3 追问：小程序和 Web 端分别怎么取首屏时间？

**微信小程序端**

`setData` 的回调只代表数据层同步完成，不保证渲染层已经绘制。要测到「内容可见」需要：

1. 在 `setData` 回调里再套一层 `wx.nextTick`，把终点打在下一帧之后；
2. 或改用官方的 `wx.getPerformance()` / `PerformanceObserver`（基础库 2.11.0+）取渲染相关指标。

> ⚠️ 这一条建议讲之前回官方文档确认一遍 API 语义。

**Web 端**

用 Performance API，不要用 `Date.now()`：

- 起点：`performance.timeOrigin` / `PerformanceNavigationTiming`（`responseStart`、`domContentLoadedEventEnd`）
- 终点：`PerformanceObserver` 监听 `paint`（FCP）与 `largest-contentful-paint`（LCP）
- 上报：`navigator.sendBeacon()`，避免阻塞页面卸载

### 3.4 记录方式的缺口

**当前没有自建的首屏耗时埋点。** 我是靠真机体感 + 性能面板发现问题并验证效果的，不是靠线上数据。这一条列在第四部分待改进项，被问到就直说。

## 四、待改进项

### 4.1 ⬜ 首屏耗时埋点与上报

**现状**：项目里没有自建的耗时埋点。存在的 `content_loaded` 是一个 0→4 的**计数**，用来决定何时撤开屏，不是耗时；`onReady` 里的 2s / 5s 两个定时器是开屏兜底，也不是埋点。

**问题**：没有数据就无法量化优化收益，也无法定位是「登录校验慢」「接口慢」还是「渲染慢」。被问"优化了多少"时只能靠体感答。

**改进方案**：

1. 小程序端在 `onLoad` 记录 `t0`，在首批列表 `setData` 回调里再套 `wx.nextTick` 记录 `t1`，上报 `t1 - t0` 作为「首屏内容可见时间」；条件允许时改用 `wx.getPerformance()`；
2. 分段上报：banner / topic / ad / post 各自完成时间分开统计，才能定位长尾在哪个数据源；
3. 把已有的 `content_loaded` 计数事件同时打点，开屏时长与首屏数据完成时间可以交叉分析；
4. 上报异步、失败不重试、不阻塞渲染。

**口述话术**：「首屏埋点这块我目前只有计数、没有耗时，是个明确的缺口。如果补，我会先分四段埋……」

### 4.2 ⬜ 其他可提的改进点

- 首屏数据请求被登录校验串行阻塞，可以评估「校验与数据请求并行 + 无 token 走游客态兜底」；
- 列表里存在用 `index` 当 key 的分支，应统一换成业务 ID，避免复用错位；
- **埋点与监控整体缺失**（方案见 2.5）：前端零上报、无异常捕获，线上问题只能靠用户反馈发现；「浏览记录」这类已有数据的触发点不可控，对外说不清口径。补的顺序建议是——先异常监控与上报通道，再曝光类埋点。

**事实边界**

| 标注 | 含义 |
|---|---|
| ✅ | 源码可证，可直接口述 |
| 🔶 | **根因**源码可证，但「你当时有没有真的遇到」按真实经历讲 |

### 5.0 一句话版本

**打开「允许主页左右滑动切换标签」之后，左右滑动切 tab 的时候，滑过去的那一页是空白的——手指按住拖动的全程看不到内容，松手之后内容才突然弹出来。我一开始以为是「四个列表同时渲染太重」，结果恰恰相反：四个 tab 共用同一份列表数据（`post_list`），结构上根本没条件给相邻页预渲染，于是只能用 `wx:if` 强行让非当前页不渲染；而更新当前页的那次状态变更又只在滑动**结束之后**才发生——两件事叠起来，拖拽期间目标页必然是空的。**

### 5.1 复现路径与应用内症状（✅ 源码可证，100% 可复现）

| 步骤 | 操作 |
|---|---|
| ① 打开开关 | 设置页 → 「允许主页左右滑动切换标签」（[setting.wxml](../../../../../tripleuni-frontend-wechat/pages/setting/setting.wxml#L44-L49)，默认关闭） |
| ② 回首页滑动 | 在首页信息流上按住，向左或向右拖动，**不要松手** |
| ③ 看拖动过程 | 目标 tab 是**空白的**，全程没有内容 |
| ④ 松手之后 | 内容出现，但列表从头重新加载，会**再闪一次骨架屏** |

两个症状是同一处设计的两种表现：

- **拖动时空白** ← 相邻页没有节点（5.3 的 ②③）；
- **松手后重新加载** ← [navbarTap](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L115-L127) 每次都把 `post_list` 清空、`page` 归零、`is_loading_more` 置回 `true`（5.3 的 ①）。

> 真机上比开发者工具更明显：按住的那几百毫秒里屏幕就是一片白，观感像「卡住了」。设置页那句「关闭后可减少误触几率」，本质上是在绕开这个体感问题。

### 5.2 定位过程

| 步骤 | 动作 | 结论 |
|---|---|---|
| ① 先证伪「性能问题」 | 第一反应是「四个 tab 的列表都在渲染，太重了」→ 打开 [home.wxml](../../../../../tripleuni-frontend-wechat/pages/home/home.wxml#L22-L36) 看渲染范围 | 只有 **1 个** swiper-item 里挂了 scroll-view，另外 3 个是空的——方向正好反了，不是渲染太多 |
| ② 找到那个唯一条件 | 定位到 scroll-view 上的 `wx:if="{{index == current_tab - start_index}}"` | 任一时刻整个 swiper 里只有一页有节点，相邻页没有内容可以提前渲染 |
| ③ 确认这是「必然」而不是「偶然」 | 追一层：为什么不能让相邻页也渲染？→ 回到 [home.js](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L115-L127) 看列表数据怎么存 | 列表只有一份 `post_list`，切 tab 时被清空、由 `current_tab` 决定拉哪个接口 → **相邻页拿不到属于它自己的数据**，让它渲染也只会画出当前 tab 的内容 |
| ④ 解释时序 | 查 swiper 的事件语义：项目只用 `bindchange`（官方定义是「current 改变时触发」）；swiper 还有 `bindtransition`（swiper-item 位置改变时触发，2.4.3+）与 `bindanimationfinish`（动画结束时触发）——**一个都没接** | 拖拽期间 `current_tab` 不变 → 目标页的 `wx:if` 仍是 `false` → 空白；松手 → `swiperChange` → `current_tab` 更新 → 内容才挂上 |
| ⑤ 查官方有没有现成方案 | 翻 swiper 组件的通用属性表 | 找到 `cache-extent`（2.29.0+），文档原文「值为 1 表示提前渲染上下各一屏区域」——**官方本来就有相邻页预渲染的能力，项目没配** |
| ⑥ 最小验证 | 临时把 `wx:if` 去掉（四页全渲染）再滑 | 跟手了、不空白了 → 确认瓶颈是「节点缺失」而不是「渲染慢」；但四页画的是同一份数据，说明要的是「预渲染相邻页」而不是「全渲染」 |

> 这一步最容易走岔：症状是「滑动不跟手」，直觉会去查 `setData` 和长列表性能（也就是 [2.4](#24-第二条线定位滑动久了卡顿) 那条线）。**先用「只有 1 个 swiper-item 有节点」这个可以直接看到的事实把性能方向否掉**，是本 bug 的关键动作。

### 5.3 根因：列表状态被四个 tab 共用（✅ 源码可证）

先看渲染这一侧——[home.wxml](../../../../../tripleuni-frontend-wechat/pages/home/home.wxml#L22-L36) 的「允许滑动」分支：

```html
<swiper current="{{swiper_current}}" bindchange="swiperChange" wx:if="{{allow_home_swipe}}">
  <swiper-item wx:for="{{navbar_items}}" wx:key="index">
    <!-- 滚动容器挂在 swiper-item 内部，且只有「当前 tab」这一页条件为真 -->
    <scroll-view ... wx:if="{{index == current_tab - start_index}}">
      <one type="{{item.type}}" data="{{item.data}}" wx:for="{{post_list}}" wx:key="index" />
    </scroll-view>
  </swiper-item>
</swiper>
```

再看数据这一侧——[home.js](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L115-L127) 切 tab 时是把**唯一的一份列表**清空重拉：

```javascript
navbarTap: function (index) {
  this.setData({
    is_loading_more: true,
    post_list: [],        // ← 四个 tab 共用同一个 post_list
    page: 0,
    scroll_top: 0,
    current_tab: index
  })
  this.getAll()           // 按 current_tab 决定调 /all、/hot、/local 还是 /topic
}
```

三件事叠在一起才构成这个 bug：

| # | 事实 | 造成的后果 |
|---|---|---|
| ① | 列表数据只有一份 `post_list`，切 tab 时被清空，由 `current_tab` 决定这次拉哪个接口 | **相邻页拿不到属于它自己的数据**——就算让它渲染，画出来的也是当前 tab 的内容 |
| ② | 因此只能把 `wx:if="{{index == current_tab - start_index}}"` 挂在 scroll-view 上，保证同一时刻只渲染一页 | 任一时刻 swiper 里只有一个 swiper-item 有节点，**相邻页是空的**；而 swiper 要跟手，必须有相邻页可渲染 |
| ③ | 更新 `current_tab` 的唯一入口是 `swiperChange`，它监听 `bindchange`——**滑动结束后**才触发 | 拖拽期间 `current_tab` 不变 → 目标页的 `wx:if` 仍为 `false` → **滑动全程空白**，松手才补上 |

> ① 是根因，②③ 是它的必然结果。这也解释了为什么「把 `wx:if` 去掉」不能算修好：四个页面会同时画同一份 `post_list`，看起来像是恢复正常，实际上是把当前 tab 的数据重复渲染了四遍。
>
> **这里有个更扎心的对照**：swiper 组件本身就有官方的相邻页预渲染属性——`cache-extent`（2.29.0+），文档原文是「值为 1 表示提前渲染上下各一屏区域（swiper 容器大小）」。我们没配它，反而用 `wx:if` 把相邻页的节点整个删掉了。而且**即使配上也没用**：相邻页没有属于自己的数据，预渲染出来的还是当前 tab 的内容——所以卡点在数据模型，不在组件配置。

**顺手带出的第二个症状**：因为数据被清空（①），每次切完 tab 都必然重新请求 → **每滑动一次就要重看一遍骨架屏**。设置页那句「关闭后可减少误触几率」，实际上是在让人绕开这个体感问题。

### 5.4 怎么修

**核心是把「一份列表」改成「每个 tab 一份」**——数据模型不对，UI 层的补丁改不动：

```javascript
// data: tabs 按 tab 索引存各自的列表与分页状态
navbarTap: function (index) {
  const cached = this.data.tabs[index]
  this.setData({
    current_tab: index,
    post_list: cached ? cached.list : [],   // 有缓存先显示，不再清空
    is_loading_more: !cached,               // 有缓存就不必进加载态
  })
  if (!cached) this.getAll()                // 只有没拉过才请求
}
```

数据分开之后，相邻页才有「属于自己的东西」可渲染，这时再让它渲染：

```html
<!-- 两个动作：① 打开官方预渲染；② 渲染范围放宽到相邻页 -->
<swiper ... cache-extent="1" wx:if="{{allow_home_swipe}}">
  <swiper-item wx:for="{{navbar_items}}" wx:key="index">
    <scroll-view ... wx:if="{{index >= current_tab - start_index - 1 && index <= current_tab - start_index + 1}}">
      ...
    </scroll-view>
  </swiper-item>
</swiper>
```

改完的效果：滑过去的那一页是**骨架屏滑进来**，松手后内容替换——从「一片白」变回正常的加载观感。

> 两个细节：一是**没有选「全部渲染」**——相邻几页的数据可能从没拉过，全渲染还会把长列表节点数推近官方建议的[单页 1000 节点上限](#59-外部依据这几类坑是小程序的通用坑不是我们独有的)；二是 `cache-extent` 只负责让相邻页「有机会」被提前渲染，**它不负责提供数据**，所以必须和「按 tab 存列表」一起用。一句话沉淀：**「渲染范围」和「数据加载范围」应该是两个独立的开关**，原来的代码把它们合并成了一个 `wx:if`。

### 5.5 口述话术

> 「印象最深的一个是：我们首页有个设置项叫『允许左右滑动切换标签』，打开之后左右滑 tab，滑过去那一页是空白的，松手内容才出来。
>
> 我的第一反应是性能问题——四个 tab 的列表都在渲染，太重了。结果打开 wxml 一看方向正好相反：**整个 swiper 里只有一页有节点**，另外三个 swiper-item 里面是空的。那我就得往下追一个问题：为什么要这么做？答案是数据结构——列表只有一份 `post_list`，切 tab 的时候直接清空重拉，由 `current_tab` 决定这次请求哪个接口。所以相邻页根本拿不到属于它自己的数据，就算放它渲染，画出来的也是当前 tab 的内容，只能用一个 `wx:if` 把非当前页全部干掉。
> 到这儿第二个症状也解释通了：既然数据每次都被清空，那每切一次 tab 就必须重新请求一次，用户滑一下就得多看一遍骨架屏。
>
> 还有个细节：更新当前页的那个 `swiperChange` 只监听了 `bindchange`。swiper 其实还有 `bindtransition`，是 swiper-item 位置改变时触发的（基础库 2.4.3 起）——我们没接。所以拖拽那几百毫秒里，当前页状态根本没变，目标页当然不渲染，这就是那片白。
>
> 修的时候我没有去硬调 `wx:if`，而是先把数据模型改成每个 tab 存一份，然后打开 swiper 官方的 `cache-extent` 预渲染属性、再把渲染范围放宽到『当前页 ±1』，让相邻页先用骨架屏顶上。滑过去就是骨架屏滑进来，而不是一片白。这里我最大的收获是：**『渲染范围』和『数据加载范围』应该是两个独立的开关**，我们原来把它俩合并成了一个 `wx:if`。」
>
> ⚠️ 如果这个开关你平时一直关着、没实际遇到过，就讲成「**做体验走查时把设置项逐个打开跑了一遍**发现的」。别讲成线上事故。

### 5.7 登录态专题：token 从哪来、失效怎么处理、怎么优化

> **这一节的组织**：实现现状（5.7.1-5.7.2）→ 那处缺陷与修法（5.7.3-5.7.4）→ bug 线的话术与追问（5.7.5-5.7.6）→ 刷新时机与请求合并（5.7.7-5.7.8）→ 设计线的话术（5.7.9）。
>
> **事实边界**：✅ 来源 / 存放 / 携带、801-802 静默续期、401-400 跳注册页、三处缺陷，都能在源码里指到；⬜ 「提前量检查」「单飞」「超时兜底」「失败幂等」在快照里**没有实现**，属设计态——口述时必须说成「我会怎么改」。

#### 5.7.1 token 从哪来、存在哪、怎么带

- **来源**：唯一入口是后端登录接口。小程序先 `wx.login()` 拿临时 `code`，再用 code 调 `/user/login/wechatuni`，后端拿 code 找微信换 `openid`、建或查用户，最后返回 **token**（[app.js](../../../../../tripleuni-frontend-wechat/app.js#L406-L418)）。前端不自己造身份，只认这个 token。
- **存放**：`wx.setStorageSync('token', res2.token)` 落本地（[app.js L418](../../../../../tripleuni-frontend-wechat/app.js#L418)），所以重启小程序不用重新授权。
- **携带**：本项目把 token **塞进请求体**，不是放 Header——[request.js L5](../../../../../tripleuni-frontend-wechat/utils/request.js#L5) 里 `Object.assign(body, { token: wx.getStorageSync('token') })`，由第三个参数 `includeToken` 控制（登录接口自己传 `false`）。
- **推论**：因为是 body 传参，**判断登录态靠的是后端业务码（801/802/401/400），不是 HTTP 401**。所以拦截点必须放在「响应里的 code」，而不是「HTTP 状态码」。

#### 5.7.2 失效分两层：静默续期 vs 回注册入口

| 层 | 触发信号 | 处理 | 用户感知 |
|---|---|---|---|
| 有效期内 | — | 正常请求 | 无 |
| 软过期（能续） | 业务码 **801 / 802** | 静默重登（`wx.login` 换新 token）→ 写回 storage → **重放原请求** | **无感** |
| 硬失效（续不了） | 重登接口返回 **401 / 400** | `wx.reLaunch` 回注册入口 + toast | 被打断，要求重新走登录 |

关键在于：**「拦截器刷新」和「弹窗跳页」不是二选一，是一条链的两级**——能续就静默续（绝大多数情况），续不了才跳页兜底（[request.js L19-L55](../../../../../tripleuni-frontend-wechat/utils/request.js#L19-L55)）。

> ⚠️ 一处必须说准：项目里跳的是**注册页** `/pages/register/register`，提示语是「请先注册」（[request.js L37-L42](../../../../../tripleuni-frontend-wechat/utils/request.js#L37-L42)），不是「登录页」。口述时说「回到注册/登录入口」比说「跳登录页」安全。

#### 5.7.3 那处缺陷：重试从来没成功过（备选 bug，开发期可复现）

> **先更正上一版的一处说法**：我原来把它讲成「token 过期时会弹一个假的『错误』提示」，重走一遍代码后这个说法**站不住**——801 分支里 `relaunchFunction()` 排在 `resolve()` **之前**，而它必然先抛 TypeError，所以 `resolve(res.data)` 根本执行不到，那个 toast 也就不会出现。**真实后果是 Promise 既不 resolve 也不 reject（悬挂），首页数据永远不来、列表一直空着。**口述时按「列表不出来」讲，别讲「弹假提示」。

- **复现路径**：开发者工具 → Storage 面板把 `token` 改成任意过期值 → 冷启动 → 首页列表为空，控制台抛 `TypeError: Cannot read property 'page' of undefined`。
- **为什么只当备选**：它要靠手动改本地存储才能触发，不是用户可达的路径；症状也只有「列表空」这一种，观感弱于 5.0。
- **三处缺陷（同一段分支）**：`relaunchFunction()` 裸调用丢了 `this`（重试根本没执行）；续期成功后 `resolve` 的是**触发续期的那次失败响应**（语义错，本该返回新响应）；401/400 分支既不 resolve 也不 reject，让上层状态机永久卡住。
- **仍然值得准备的原因**：下面的「四条规则」可以迁移，尤其是「每条分支都必须 settle」——这条同时解释了 5.8 里三个失败路径问题的成因。

#### 5.7.4 怎么修（清单 + 四条可迁移规则）

**修①：调用方传闭包，别传方法引用**

```javascript
// pages/home/home.js
newRequest("/post/list/all", { page: that.data.page }, () => that.getPost())
```

**修②：把「续期」收敛成一次带锁的流程**——它同时就是「请求合并」的落地形态：单飞、超时兜底、失败幂等都在里面，完整代码见 5.7.8。

**四条可以带走的规则**

1. **透明重试的语义是「调用方拿到最终那次的结果」**。中途失败的那次响应只能用于判断，不能当返回值——否则调用方看到的是一个已经被自己内部处理掉的错误。
2. **方法引用 ≠ 回调**。传 `that.getPost` 会丢 `this`，要么传 `() => that.getPost()`，要么 `that.getPost.bind(that)`。
3. **静默续期必须「单飞 + 有上限」**：同一时刻只允许一次重登（并发请求同时过期时不应该各登一次），重试要有次数上限（否则 token 一直无效就是死循环）。项目里已经有同款正例——[app.js](../../../../../tripleuni-frontend-wechat/app.js#L753-L788) 的 `pendingNoticeRefresh` 和 [app.js](../../../../../tripleuni-frontend-wechat/app.js#L887-L901) 的 `pendingChatDetailTimer` 都是「同一件事并发只做一次」的写法，可以直接照搬（完整落地版——带 key 化、超时兜底、失败幂等、多页面边界——见 5.7.8）。
4. **每条分支都必须 settle**：`resolve` 和 `reject` 二选一，绝不能都不选。Promise 悬挂比抛错难查得多——**抛错至少还有一行日志，悬挂是静默的**。

#### 5.7.5 口述话术（故事 A：那个「重试没成功」的 bug）

> 「还有一个印象比较深的，是在公共请求封装里翻出来的：token 过期的时候，小程序会自己重新登录然后重试原请求，但这个『重试』从来没成功过——首页列表是空的，控制台只有一条 TypeError。
>
> 复现很直接：开发者工具里把 storage 里的 token 改成过期值，冷启动，首页就空着。
>
> 定位的关键动作是看 Network 面板：**只有第一次请求，第二次根本没发出去**。这一步推翻了『重试失败』的假设——不是失败，是压根没执行。回去看那行调用就明白了：调用方传进来的是页面方法 `that.getPost`，而封装层是裸函数调用的，`this` 丢了；页面方法第一件事就是读 `this.data.page`，所以直接抛 TypeError。
>
> 顺手还发现同一段分支另外两处问题：续期成功之后，它 `resolve` 的是**触发续期的那次失败响应**，而不是重试后的新结果；还有一个分支既不 resolve 也不 reject，会让上层状态机永久卡住。修法就是三件事：调用方传闭包、续期改成『单飞 + 有次数上限』、并且返回重试后的新响应。沉淀成两条：**透明重试要返回最终结果**，以及**每条分支必须 settle**——Promise 悬挂比抛错可怕，因为它连日志都没有。」
>
> ⚠️ 讲这段的重点是「**用『请求有没有发出去』去证伪假设**」这个方法，不是 bug 本身。

#### 5.7.6 追问防线

| 会被问 | 怎么答 |
|---|---|
| 你怎么确定是 `this` 丢了，而不是网络没通？ | 复现时看 Network 面板：只有第一次请求，没有第二次。重试压根没发起，就不可能是网络问题 |
| 严格模式和非严格模式下 `this` 不一样，结论变吗？ | 不变。严格模式是 `undefined`，非严格模式是全局对象——两种都不含 `data`，读 `that.data.page` 一样抛错 |
| 为什么不干脆在封装层做重试？ | 可以做，但封装层必须知道「重试后要返回新响应」以及「重登要单飞」。项目里其他正例（`pendingNoticeRefresh`）就是这么做的，说明这个思路在本项目里是成立的 |
| 并发请求同时过期会怎样？ | 每个请求各自走一遍 `wx.login` + 登录接口，并发重登互相覆盖 token（首屏 4 路并发就是 4 次重登）。所以要单飞，让后来者复用同一个「刷新中」的 Promise |
| 重登也失败怎么办？ | 有次数上限直接抛错，交给调用方兜底（提示 + 引导重新授权），不能无上限重试 |
| 这类问题怎么在线上发现？ | 这正是本项目最大的缺口——**前端零上报、无异常捕获**（见 [4.2](#42--其他可提的改进点)）。这个 bug 只能靠控制台和用户反馈发现，补的顺序是先异常监控、再埋点 |
| 为什么不提前用 exp 判断，非等失败？ | 可以判断，但只能当优化。客户端时钟不可信，且 token 可能提前失效——响应侧兜底无论如何都得有，既然必须有，就把它当唯一入口 |
| 刷新请求自己也过期了怎么办？ | 刷新请求不能走同一套拦截，否则递归；它失败就直接进「硬失效」分支，清登录态 + 跳页 |
| 跳页会不会跳很多次？ | 会，不做幂等就会。要加标志位，保证只跳一次 |
| 为什么不用定时刷新？ | 小程序切后台会挂起 JS，定时器不可靠；空闲时白刷；多页面各自定时还会互相竞争。定时器最多作为「刷新成功后的预估」辅助 |
| token 为什么放 body 不放 Header？ | 这是本项目的既定约定（后端按 body 取），**不是最佳实践**。放 Header 的 `Authorization` 更通用，也便于按标准 401 统一拦截——要如实说，别包装成设计选择 |
| 客户端存 token 安全吗？ | 小程序 storage 相对封闭，但仍是本地数据，不能当可信凭证；真正的约束在后端（有效期短、可主动作废）。Web 端还要考虑 XSS，优先 httpOnly Cookie |


#### 5.7.7 刷新函数该放在什么时候执行（这道题真正的考点）
**结论：主力放「响应侧」——等后端明确说过期了再刷；请求前的「提前量检查」只做优化；不要用纯定时器。**

1. **过期与否只有服务端说了算。** 客户端时钟可能不准甚至被篡改，token 还可能因为改密码、被踢、封号而**提前失效**。所以「读响应里的过期信号」是唯一可靠的防线——既然可靠防线必须在这里，刷新逻辑就该收口在这里。
2. **入口唯一。** 可靠防线已经落在响应侧，就不该再维护第二套刷新逻辑，否则一定会出并发问题（两套逻辑各自刷新、互相覆盖 token）。
3. **请求前的提前量只是优化。** 读到 token 剩余时间不足阈值（如 60s）就先刷再发，可以把「先失败一次、再刷新、再重试」那一个额外 RTT 提前消化掉，用户更无感；但受第 1 条限制，它不能当唯一防线。
4. **纯定时器不合适。** 小程序切后台会挂起 JS（定时器不准）、用户不操作时白刷、多页面各起一个定时器还会互相竞争。

**比「放哪里」更重要的是「并发怎么处理」**——单飞、队列重放、排除刷新接口自身、失败幂等、成功三处同步，这五条统一收进 5.7.8 的落地清单，这里不重复。

**放在哪一层**：不放在业务页面（会散落、重复），放在统一请求层。本项目就是 [request.js](../../../../../tripleuni-frontend-wechat/utils/request.js) 的 `newRequest`，Web 端的等价物是 axios 的响应拦截器。可改进点：现在「跳注册页」这个**导航副作用直接写在请求层里**，请求层的理想职责是「settle 结果 + 抛出可识别的错误码」，跳转交给上层或回调——这样解耦，也好测。

Web 端的骨架长这样（小程序端的完整实现在 5.7.8）：

```javascript
// axios 响应拦截器：懒触发 + 单飞 + 只重放一次
let refreshPromise = null

instance.interceptors.response.use(
  (res) => res.data,
  async (err) => {
    const { config, response } = err
    if (response?.data?.code !== 801 || config._retry) return Promise.reject(err)

    config._retry = true                                                   // 只重放一次
    refreshPromise ||= doRefresh().finally(() => { refreshPromise = null }) // 单飞
    try {
      await refreshPromise
    } catch (e) {
      clearAuth(); redirectToLogin()                                       // 刷新也失败 → 幂等跳页
      return Promise.reject(e)
    }
    config.headers.token = getToken()                                      // 用新 token 重放
    return instance(config)
  }
)
```

#### 5.7.8 请求合并的完整落地（结合业界最佳实践）

**第一步：先把模式名认准。** 我们要的东西在业界叫 **单飞（single-flight）**，也叫请求合并（request coalescing）：**同一个 key 的并发调用只真正执行一次，其余全部复用它那一个结果**。它不是节流（throttle 限制频率），也不是限流排队。

两种常见实现风格，做的其实是同一件事：

| 风格 | 做法 | 适用 |
|---|---|---|
| 共享 Promise（单例） | 把「刷新中」的 Promise 存起来，后来者直接返回它 | JS 单线程 + Promise 天然可共享，前端首选 |
| 显式请求队列 | 维护 `isRefreshing` 布尔 + `queue` 数组，刷新完成后逐个重放 | 需要精细控制每个失败请求各自的重放参数 |

前端 401 场景里这两种常被**混用**：用共享 Promise 保证「只刷一次」，用各自重放保证「每个请求拿回自己的结果」——这正是本项目 `requestWithRetry` 应有的形态。

**第二步：六个必须补上的实现细节**（5.7.4 的规则 3 只说「要单飞、要有上限」，这里把它落成具体写法）：

1. **锁的 key** 用「触发失败时那一份**旧 token**」。同一批并发请求带的是同一个旧 token，自然命中同一个 key。
2. **`finally` 释放锁**：成败都要删 key。只在成功时释放的话，一旦刷新失败，后续请求会被**永久挡在门外**。
3. **超时兜底**：第一次刷新若卡住（挂起的网络），所有等待者会一起卡死。要给刷新加超时（如 8s），超时按失败处理——这是 5.7.4 规则 4「每条分支必须 settle」的另一面。
4. **失败幂等**：并发失败时 `reLaunch` 只能触发一次（用 `redirecting` 标志位），否则会连跳 N 次登录/注册页。
5. **重放上限**：`_retry` 标记 / 次数上限，只重放一次，避免「刷新成功但原请求仍失败」时无限循环。
6. **刷新接口绕开拦截**：登录接口自己不能走那条会触发刷新的分支（项目已用 `includeToken = false` 做到一半，还要保证它不回落到 801/802 分支）。

**第三步：小程序端的完整实现**（5.7.4 修复清单的落地版）：

```javascript
// utils/request.js —— 请求合并版：单飞 + 队列重放 + 超时 + 失败幂等
const inflight = new Map()      // key: 旧 token → value: 刷新中的 Promise
let redirecting = false         // 跳页幂等
const RETRY_MAX = 1             // 只重放一次

function withTimeout(p, ms) {
  return Promise.race([
    p,
    new Promise((_, reject) => setTimeout(() => reject(new Error('relogin timeout')), ms)),
  ])
}

function reloginOnce(key) {
  if (!inflight.has(key)) {
    const p = withTimeout(doRelogin(), 8000)
      .finally(() => inflight.delete(key))   // 成败都释放，否则后续全被挡住
    inflight.set(key, p)
  }
  return inflight.get(key)                   // 后来者复用同一个 Promise
}

function handleHardFail() {
  if (redirecting) return                    // 并发失败只跳一次
  redirecting = true
  wx.removeStorageSync('token')
  wx.reLaunch({ url: '/pages/register/register', complete: () => { redirecting = false } })
}

async function requestWithRetry(path, body, opts, retried = 0) {
  const staleToken = wx.getStorageSync('token')   // 拿旧 token 当 key
  const res = await rawRequest(path, body, opts)
  if (res.code !== 801 && res.code !== 802) return res
  if (retried >= RETRY_MAX) throw new Error('登录态失效')

  try {
    await reloginOnce(staleToken)                 // ← 4 个并发只有 1 次真刷新
  } catch (e) {
    handleHardFail()
    throw e
  }
  return requestWithRetry(path, body, opts, retried + 1)  // 各自用新 token 重放
}
```

效果对比：首屏 4 路并发过期，原来是 **4 次 `wx.login` + 4 次登录接口**，改后是 **1 次刷新 + 4 次重放**。

**第四步：服务端要配合的两件事**（不然客户端做得再对也会随机掉线）：

- **宽限窗口（grace window）**：允许旧 refresh token 在刷新后的一小段时间内仍可用（业界常见 30 秒级），兜住「请求刚过期、新 token 刚写入」这种并发。
- **原子轮换 + 复用检测**：轮换新 token 时用原子操作，避免两个请求各拿到一个「有效」的 token；对「已用过的 refresh token 再次出现」做检测（可能意味着 token 泄露）。

**第五步：多页面 / 多标签页的边界**（面试加分）：

- 本项目是**单个小程序**：所有页面共享同一个 JS 逻辑层，所以把锁放在模块级别（`app.js` 里的单例）就够了——这正是 `pendingNoticeRefresh` 的做法。
- 换成 **Web 多标签页**就不够了：**进程内的锁管不住另一个标签页**。那种场景要让一个标签页负责刷新，其余通过 `BroadcastChannel`（或 `storage` 事件）接收新 token，否则两个标签页各自轮换会互相作废——这是「用户随机掉线」的经典成因。

**为什么开发时发现不了**：单飞问题只在**真并发**下暴露。开发时一个个点、请求基本串行，永远看到「刷新成功」；只有首屏并发或用户手快连点时才炸。这也是它值得单独准备的原因。

#### 5.7.9 口述话术（故事 B：登录态该怎么设计）

> 「我们的登录态就一个 token。小程序启动时 `wx.login` 拿 code 去换 token，存在 storage 里，之后每个请求都带上它。
>
> 过期分两种。一种是 token 过期但还能续——后端返回 801/802，我们在统一请求封装里接住，静默重新登录换新 token，再把原请求重放一遍，用户完全无感。另一种是真的续不了——重登接口返回 401/400，这时候才把用户拉回注册入口。
>
> 如果让我重新设计，刷新时机我会放在**响应侧**，不用请求前判断、更不用定时器。原因是：过期这件事不由客户端决定——本地时钟可能不准，服务端还可能因为改密码、异地登录提前把 token 作废。所以『等后端说过期了再刷』是唯一可靠的防线。请求前做一次『剩余时间不够就先刷』只是优化，能省掉一次失败重试的往返。
>
> 而真正难的不是放在哪，是**并发**：多个请求同时过期时，怎么保证只刷一次、其余请求排队等新 token 再重放；以及刷新失败时别重复跳页。这几条恰恰是我们当时没做好的地方。」
>
> ⚠️ 讲这段的落点是「**为什么可靠防线只能是响应侧**」，加上「并发控制」这个加分项，不是背拦截器写法。


### 5.8 同类的另外三个（也都满足两个准入标准：一键可复现 + 应用内可见）

共同根因一句话：**失败路径没写**。整个 `pages/` 目录只有 4 处 `.catch`（[detail.js](../../../../../tripleuni-frontend-wechat/pages/detail/detail.js#L297)、[enterTripleUni.js](../../../../../tripleuni-frontend-wechat/pages/enterTripleUni/enterTripleUni.js#L49)、[home.js](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L430)、[pmdetail.js](../../../../../tripleuni-frontend-wechat/pages/pmdetail/pmdetail.js#L235)），业务请求基本只写 `.then`；而 `newRequest` 在网络失败时是 `reject`（[request.js](../../../../../tripleuni-frontend-wechat/utils/request.js#L71-L73)）——「失败」这件事在业务页面里几乎不存在。

| # | 复现路径 | 应用内看到什么 | 根因 |
|---|---|---|---|
| A | 开发者工具把网络切成「离线」→ 用**已登录账号**冷启动 → 恢复网络 → 等 10 秒 | 首页**一直挂着骨架屏**，不会自己加载回来；只能手动下拉刷新或杀掉重进 | [app.js](../../../../../tripleuni-frontend-wechat/app.js#L61-L65) 的 `launch().then()` 没有 `.catch`，请求失败时 `token_checked` 永远不置位；而首屏四个请求只挂在 `token_checked` 的监听里（[home.js](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L665-L687)）→ 首屏一个请求都没发出去；骨架屏的显示条件又是「`is_loading_more` 为真且 `post_list` 为空」，而 `is_loading_more` 初值就是 `true` → 三处叠加 = 永久骨架屏 |
| B | 详情页 → 开发者工具切「离线」→ 点赞 → 恢复网络 → 退出详情页再进 | 红心是亮的、数字 +1，但服务器没记录；重进后点赞消失 | [detail.js](../../../../../tripleuni-frontend-wechat/pages/detail/detail.js#L489-L516) 的乐观更新只写了「先改本地 + 成功校正 + 业务码失败回滚」；**网络失败走的是 `reject`，没写 `.catch`** → 乐观状态永不回滚。同一个项目里 [pmdetail.js](../../../../../tripleuni-frontend-wechat/pages/pmdetail/pmdetail.js#L235-L244) 发消息就写对了（catch 里 toast + `slice(0, -1)` 回滚），可以直接拿来做对照 |
| C | 已加载若干页后切「离线」→ 滚到底触发一次加载 → 恢复网络 → 继续滚 | 列表底部**一直显示「加载中...」**，再也不加载下一页；下拉刷新虽然能救回来，但列表会重置回第一页 | [onLoadMore](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L66-L78) 先把 `is_loading_more` 置 `true`、`page + 1`，请求失败后没有任何复位；而 `bindScroll` / `onLoadMore` 都以这个锁为早退条件 → 锁永久为 `true`（底部文案来自 [loadmore.wxml](../../../../../tripleuni-frontend-wechat/components/loadmore/loadmore.wxml#L2-L5)） |

> B 和 C 是同一个根因的两种表情：一个是**乐观状态没回滚**（数据撒谎），一个是**状态锁没复位**（功能冻结）。讲的时候把它们归到「失败路径没写」这一句上，比单讲一个更有分量。
>
> 唯一**不满足准入标准**的候选是 [imageCache.js](../../../../../tripleuni-frontend-wechat/utils/imageCache.js#L21-L72) 的重复下载。**这里要更正一版说法**：它并不是「只增不减直到撑爆 200MB」——`getImageCache` 全项目只有两个调用点、而且 key 是固定的（[home.js](../../../../../tripleuni-frontend-wechat/pages/home/home.js#L420) 的 `openAd`、[detail.js](../../../../../tripleuni-frontend-wechat/pages/detail/detail.js#L289) 的 `detailAd`），每个 key 只留一个文件，孤儿文件要「后端换一次素材」才多一个，没有爆量路径。它真实的缺陷是两个：**同一张图在缓存失效时被下载两次、存两份**（白费流量），以及 **`saveFile` 没写 `fail`，写盘失败时 Promise 永不 settle**（图片直接不显示）。用户感知太弱，所以没进主答案——但它复用的正是 5.7 那条「每条分支必须 settle」的规则，可以当补充说。
