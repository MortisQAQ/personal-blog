# 02｜流式布局与内容驱动设计：先让内容排得下，再决定何时换结构

[返回阅读指南](./00-阅读指南.md) · [上一篇：视口像素与尺寸基础](./01-视口像素与尺寸基础.md) · [下一篇：媒体查询与容器查询](./03-媒体查询与容器查询.md)

继续搭建“前端课程与资讯”页面。第一篇已经为它建立了合适的视口、保留用户字号的根设置和有最大宽度的容器。现在要让筛选按钮、课程卡片和课程资料在各种可用宽度下成立。

最容易想到的做法是：桌面固定三列，手机把页面缩小。这个想法遗漏了一个前提：阅读页面的内容不是固定图片。标题会变长，课程可能只剩两门，用户可能放大文字，组件也可能被放到侧栏。浏览器必须同时满足外部空间约束和内部内容需求。理解这两股力量，才能解释“我明明写了 1fr，为什么还会溢出”。

本文先从普通流推导内在尺寸，再计算 Flex 和 Grid 的空间分配。示例均为教学片段，不依赖框架，不需要新建 HTML 测试文件。演算默认横向书写、根字号 16px；涉及布局预算时会明确是否忽略边框和 padding。390、834、1440 是观察宽度；768、1024、1440px 是本仓库使用的视口断点约定，并非全球统一标准。本篇让大部分布局在没有媒体查询的情况下自然适应，结构切换留到第三篇。

## 一、普通流本身已经具有适应性

先不写 Flex 或 Grid，只放入几段课程内容：

```html
<main class="course-page">
  <h1>前端课程与资讯</h1>
  <p>用真实内容理解浏览器如何安排空间。</p>
  <section aria-labelledby="courses-heading">
    <h2 id="courses-heading">最新课程</h2>
    <article class="course-card">
      <h3><a href="/courses/layout">从普通流理解现代布局</a></h3>
      <p>本课解释行宽、换行与卡片高度之间的关系。</p>
    </article>
  </section>
</main>
```

在普通流中，常见块级盒子沿块轴依次排列；横向书写时看起来就是从上到下。段落里的行内内容沿行内轴排布，可用宽度不足时，根据语言和换行规则进入下一行。父级高度通常由这些内容形成，后面的文章会随着前面文章变高而向下移动。[MDN 普通流指南](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Display/Block_and_inline_layout)解释了块与行内格式化的基础。

这意味着：给容器一个弹性宽度、允许文本换行、不给卡片锁死高度，就已经得到了一种响应式行为。窄屏上的标题多出一行，卡片因此变高，是内容正确参与布局的结果。若把所有卡片设为 `height: 12rem`，就切断了这条关系；简介多一点、用户字号大一点，就可能覆盖入口或被裁掉。

```css
/* 错误：把某一次截图的高度当作内容永久不变的事实 */
.course-card { height: 12rem; overflow: hidden; }

/* 修正：让内容撑高；需要视觉基线时只给最小高度 */
.course-card { height: auto; min-height: 12rem; }
```

最小高度也不是必需项，只有设计确实需要时才加。普通流还有外边距折叠等规则，不应把相邻 margin 一概当成简单相加；后面列表使用 Grid 的 gap 来表达卡片间距，会更直接。

## 二、内在尺寸：先问内容愿意多宽

外部给定 `width: 300px` 属于作者从外向内施加的约束；内在尺寸则从内容本身出发。想象把课程标题单独拿出来，问两个极端问题：如果尽量不软换行，它需要多宽？如果把所有允许的软换行都用上，它还能缩到多窄？这分别通向 max-content 和 min-content。

### max-content 与 min-content 不是最长文本与最短文本

假设标题是 `Responsive layout foundations`，为便于演算，假设测量得到不软换行时为 280px，最长不可断片段 `foundations` 为 110px。在当前字体和换行规则下，可以用以下模型理解：

```text
max-content ≈ 280px：不在普通软换行机会处分行
min-content ≈ 110px：尽可能分行，仍要容纳不可再断的片段
```

这不是固定的字符串长度公式：字体、字号、字距和语言都会改变结果；手动强制换行仍会被保留。中文通常存在更多字间换行机会，长 URL 的策略又不一样。因此不能永远把 min-content 定义为“最长单词宽度”，那只是常见西文文本在默认换行规则下的直观例子。见 [MDN min-content](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/min-content)。

```css
.title-min { inline-size: min-content; }
.title-max { inline-size: max-content; }
```

前者可能形成很窄、很高的标题盒子；后者可能直接超过手机宽度。它们描述内容的内在需求，不保证适合外部空间。

### fit-content 如何在内容需求与可用空间之间折中

对于盒子的 `inline-size: fit-content`，先忽略额外边距、边框等，让可用空间为 A，可以理解为：

```text
结果 = min(max-content, max(min-content, A))
```

沿用最小 110px、最大 280px 的标题：A 为 400px 时结果是 280px，不会无意义地铺满；A 为 180px 时结果是 180px，内容换行；A 为 80px 时结果却为 110px，仍可能溢出。这最后一种情况很关键：fit-content 保留最小内在需求，不是强制防溢出的魔法。[MDN fit-content 关键字](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/fit-content)给出了完整公式，实际 stretch 项还涉及盒模型。

Grid 的 `fit-content(20rem)` 是带参数的轨道函数，不要与盒子上的 fit-content 关键字混为一谈。它限制轨道向内容最大尺寸增长，但仍受自动最小尺寸约束；遇到不可断长串，轨道仍可能超过参数。需要硬性控制空间时，要同时处理最小尺寸和内容换行，不能只看函数名称。

## 三、Flex：先确定基准，再分配余量或不足

筛选栏适合用 Flex：按钮长短不同，主要关心一条轴上的排列，空间不够可以整项换行。

```css
.course-filters {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem;
}
.course-filters button {
  font: inherit;
  padding: 0.5em 1em;
  white-space: normal;
  overflow-wrap: anywhere;
  max-inline-size: 100%;
}
```

`flex-wrap: wrap` 允许换行，但一项自身若有 100 个字符的不可断文本，也可能超过整行，所以仍需要内容策略。换行发生后，每条 Flex 行独立计算空间，不能把它当作跨行对齐的二维表格。

为了理解算法，先限定单行、横向主轴，忽略 margin、padding、border、gap，并假设没有 min/max 约束介入。真实页面必须把这些预算加回去。

### flex-basis 决定从哪里开始分配

```css
.course-summary { flex: 1 1 200px; }
.course-detail  { flex: 2 1 200px; }
```

三个值分别是 grow、shrink、basis。basis 是参与主轴分配的起点，不是“最后一定有这么宽”。如果容器 800px，两个起点共 400px，还剩 400px。grow 为 1 和 2，所以新增空间按 1:2 分：

```text
第一项 = 200 + 400 × 1/3 ≈ 333.33px
第二项 = 200 + 400 × 2/3 ≈ 466.67px
合计 = 800px
```

grow 比例分配的是剩余空间，不是最终宽度。因此 grow 为 2 的第二项，最终宽度没有达到第一项的两倍。如果两项 basis 都为 0，并且没有其他约束，最终宽度才更接近 grow 比例。常用 `flex: 1` 在浏览器中通常展开为 `1 1 0%`；教学时写完整值更便于看清前提，尤其不要把它当成 `1 1 auto`。

`flex-basis: auto` 在水平主轴上会先参考 width，width 也是 auto 时再由内容决定；百分比 basis 需要可确定的容器主轴尺寸，否则其使用值会转向 content。详情见 [MDN flex-basis](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/flex-basis)。

### shrink 为 1，为什么不各减同样多

把容器改成 500px，两项 basis 分别 400px 与 200px，shrink 都为 1。起点总计 600px，需要消化 100px 负空间。浏览器按收缩因子与基准尺寸的乘积加权：

```text
第一项权重 = 1 × 400 = 400
第二项权重 = 1 × 200 = 200
第一项减少 = 100 × 400/600 ≈ 66.67px
第二项减少 = 100 × 200/600 ≈ 33.33px
最后宽度 ≈ 333.33px 与 166.67px
```

如果简单各减 50px，小项承受的相对缩减比例会更高。乘上基准尺寸，就是让 shrink 相同的项目在没有其他约束时按相近比例收缩。若第二项 shrink 改为 2，权重就变成 400 和 400，这次才各减 50px，得到 350px 与 150px。[MDN flex-shrink](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/flex-shrink)说明了负空间分配及加权依据。

### min-width: auto 为什么能挡住收缩

以上计算都有一个限定：没有最小尺寸约束。实际 Flex 项的主轴自动最小尺寸在常见、非滚动容器场景下会保留基于内容的下限，通常与 min-content 有关，还可能受指定尺寸、宽高比等影响。所以 `flex-shrink: 1` 不等于允许压到任意宽度。

沿用上一例，若第一项的内容最小需求是 360px，初步算出的 333.33px 违反下限，第一项就会停在 360px；第二项必须进一步缩到 140px，才能合计 500px。若第二项的最小需求又是 160px，那么 `360 + 160 = 520px`，两项就仍然超宽。算法会冻结受约束项并重新分配，而不是只做一次减法。

当第一项是课程正文、允许长标题换行时，可以明确解除盒子的自动最小尺寸：

```css
.course-row {
  display: flex;
  gap: 1rem;
}
.course-row__body {
  flex: 1 1 0;
  min-width: 0;
  overflow-wrap: anywhere;
}
.course-row__action {
  flex: 0 0 auto;
}
```

横向书写中也可写逻辑属性 `min-inline-size: 0`。这个修正分成两个责任：最小尺寸规则允许盒子变窄；换行规则让内容能在窄盒子中排布。只设 min-width 为 0，内部 `white-space: nowrap` 的内容仍然可能跑出去。也不要默认在整行加 `overflow: hidden`，那会把阅读内容和焦点轮廓一起裁掉。自动最小尺寸的例外与条件可结合 [MDN flex-basis](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/flex-basis)中的说明阅读；本例针对常见横向内容行，不泛化成“auto 永远等于 min-content”。

## 四、Grid：fr 分的是剩余空间，也有最小尺寸前提

课程卡片需要行列对齐，适合 Grid。先看一个有明确可用宽度的预算：容器内容区 1000px，一列固定 200px，另外两列分别 1fr、2fr，两个 gap 各 20px。

```css
.course-layout {
  display: grid;
  grid-template-columns: 200px minmax(0, 1fr) minmax(0, 2fr);
  gap: 20px;
}
```

扣掉固定列和间距后，剩余 `1000 - 200 - 20 × 2 = 760px`。两条弹性轨道分为三份，分别约 `253.33px` 与 `506.67px`。fr 不是“整个容器的比例”，它参与的是轨道算法中的剩余空间分配；在可用尺寸不确定或内容约束介入时，计算不能一概简化成这张算术表。

为什么这里写 `minmax(0, 1fr)` 而不是裸 `1fr`？因为单独的 fr 轨道隐含自动最小值，可理解为 `minmax(auto, 1fr)`。一个长 URL、不可换行的 pre 或有宽高比的媒体，可能通过内容贡献把轨道下限抬高，使本来以为均分的列突然变宽。[MDN grid-template-columns](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/grid-template-columns)与 [minmax](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/minmax)说明了这些边界。

```css
/* 容易误判：以为 1fr 必然允许列压得足够窄 */
.course-grid { grid-template-columns: repeat(3, 1fr); }

/* 显式允许轨道最小值为 0，但还需处理内部内容 */
.course-grid { grid-template-columns: repeat(3, minmax(0, 1fr)); }
.course-card { min-inline-size: 0; overflow-wrap: anywhere; }
```

`minmax(0, 1fr)` 处理轨道下限，`min-inline-size: 0` 处理项目自身下限，内容的换行或局部滚动处理绘制结果。这几个层次相关，却不是互相替代的同一件事。三列固定数量也不会凭空适合 390px：这里只是解释轨道机制，接下来让列数自然变化。

## 五、让列数从空间与内容需求中长出来

继续使用第一篇的稳健容器：

```css
.course-page {
  width: min(calc(100% - 2rem), 72rem);
  margin-inline: auto;
}
.course-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr));
  gap: 1rem;
}
```

先逐层读，不要把它背成咒语。容器在窄处扣掉总计 2rem 的两侧空间，在宽处停在 72rem。Grid 希望每列以 16rem 为可用的最小阅读宽度，以 1fr 分享剩余空间；repeat 的 auto-fit 根据可用宽度安排尽可能多的轨道，并折叠空轨道。

如果只写 `minmax(16rem, 1fr)`，当嵌套容器本身只有 230px，而根字号 16px、16rem 等于 256px 时，即使只排一列也放不下。于是最小值改成 `min(100%, 16rem)`：在宽容器中取 256px，在窄容器中取其全部可用宽度。它表达“希望至少 16rem，但不能因此强迫外部容器超宽”。这里的 100% 以 Grid 容器的相关尺寸为基准；本例依靠外层给出可确定的行内空间，不应忽略百分比在内在尺寸计算中的专门规则。

假设卡片数量足够填满首行，根字号 16px，gap 为 16px，外层没有额外 padding 和 border。对于 n 列，最低需求为：

```text
n × 256 + (n - 1) × 16 ≤ 容器宽度
```

| 视口观察宽度 | 页面容器宽度 | 可容纳列数 | 每列实际宽度 |
| --- | --- | --- | --- |
| 390px | 358px | 1 | 358px |
| 834px | 802px | 3 | (802 - 32) ÷ 3 ≈ 256.67px |
| 1440px | 1152px | 4 | (1152 - 48) ÷ 4 = 276px |

834px 出现三列不是计算错误：我们选择的最小阅读宽度允许这样安排。若课程标题更长、封面需要更多空间，应该提高卡片的合理最小宽度，或在需要明确结构变化时使用查询。不能因为某设备被叫作平板，就认定它只能有两列。这里列数改变的临界点来自内容与空间预算，不是新增一个项目视口媒体查询断点。相关思想也见 [web.dev Grid 教程](https://web.dev/learn/css/grid)及[响应式设计基础](https://web.dev/articles/responsive-web-design-basics)。

### auto-fit 与 auto-fill 的真正差异在空轨道

设容器 1000px，最小列宽 240px，gap 为 20px。四列最低需要 `4 × 240 + 3 × 20 = 1020px`，放不下；三列需要 760px，能放下。若有至少三张卡片，auto-fit 与 auto-fill 在这个首行可能看不出区别。

如果整个网格只有两张卡片，auto-fill 仍保留第三条空轨道，三条轨道各约 `(1000 - 40) ÷ 3 = 320px`，前两条放卡片，第三条空着。auto-fit 则在放置后折叠空轨道及相邻相关间距，两张卡片分享空间，各为 `(1000 - 20) ÷ 2 = 490px`。这就是稀疏列表中卡片变宽的原因，详见 [MDN repeat](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/repeat)。

不要进一步误解为“auto-fit 总把最后一行两张卡片撑满”。假设总共有五张卡片，三列中每一列都已在第一行被占用，最后一行剩两张并不会使第三列成为整条空轨道，因此通常仍按三列网格对齐。空轨道和某一行的空单元格，是两个不同概念。若希望少量课程仍保持接近常规卡片宽度，可考虑 auto-fill；希望少量课程充分占满行，则考虑 auto-fit，并接受大卡片结果。

## 六、嵌套内容如何把溢出一路传给外层

一个常见现场是：页面宽度正确，网格列用了 minmax，仍然有横向滚动。原因可能藏在卡片中的课程详情行：详情行是 Flex，正文区有自动最小尺寸，里面又有一个 `white-space: pre` 的代码块。最里面的长行提供了很大的内在宽度，外层某个尚未解除的最小尺寸限制会把这个需求传上来。

定位时按层问三个问题：这一层的可用宽度从哪里来？这一层的最小尺寸是否允许它变窄？内部内容变窄后会换行、滚动还是溢出？不要只在最外面的 body 上隐藏横向溢出。

```css
.course-grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr));
  gap: 1rem;
}
.course-card,
.course-card__body {
  min-inline-size: 0;
}
.course-card__body {
  overflow-wrap: anywhere;
}
```

这不是要求所有 DOM 元素都无条件加 min-width 为 0，而是在产生约束的 Grid 项、Flex 项等关键边界上明确意图。对每层实际格式化上下文进行解释，比全局通配符补丁更容易维护。

### 普通文字、长 URL 和代码不是同一种内容

普通段落优先使用语言本身的换行规则；标题和 URL 需要应急断行时可以设置 `overflow-wrap: anywhere`。它允许无正常断点的长串在必要时断开，并把这些机会计入 min-content 计算；`break-word` 虽然也能应急断行，却不以同样方式影响 min-content。[MDN overflow-wrap](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow-wrap)明确区分了两者。

```css
.course-card__title,
.course-card__summary,
.course-card__source {
  overflow-wrap: anywhere;
}
```

不要为了解决一条 URL，在所有文本上设置 `word-break: break-all`。它可能把正常西文单词也拆得难读。也不要先设 `white-space: nowrap` 再期待 overflow-wrap 按普通段落方式救场，前者已经阻止了软换行。

代码和表格可能有保留横向关系的需要。代码若随意换行会影响辨认，课程对比表若把每列挤到几个字宽，也可能更难理解。因此允许**局部**横向滚动，保持页面本身不横向溢出：

```html
<pre class="course-code" tabindex="0" aria-label="课程布局代码"><code>.course-grid { display: grid; grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr)); }</code></pre>

<div class="course-table-scroll" role="region" aria-labelledby="compare-caption" tabindex="0">
  <table>
    <caption id="compare-caption">课程主题、时长与前置知识对比</caption>
    <thead><tr><th scope="col">课程</th><th scope="col">时长</th><th scope="col">前置知识</th></tr></thead>
    <tbody><tr><th scope="row">响应式布局</th><td>6 小时</td><td>HTML 与基础 CSS</td></tr></tbody>
  </table>
</div>
```

```css
.course-code,
.course-table-scroll {
  max-inline-size: 100%;
  min-inline-size: 0;
  overflow-x: auto;
}
.course-code { padding: 1rem; white-space: pre; }
.course-table-scroll table {
  inline-size: 100%;
  min-inline-size: 36rem;
  border-collapse: collapse;
}
.course-table-scroll th,
.course-table-scroll td {
  padding: 0.75rem;
  text-align: start;
}
.course-code:focus-visible,
.course-table-scroll:focus-visible {
  outline: 2px solid currentColor;
  outline-offset: 2px;
}
```

36rem 是这个教学表格为保留列关系选择的内容下限，不是页面布局断点。外层滚动区域保持受约束，内层表格可以更宽；若当前表格非常简单，当然可以取消这个下限。示例显式提供可聚焦入口和可理解名称，让键盘用户也能到达并滚动区域，不能只验证触屏横滑。保留可见的滚动线索，避免用户以为被裁掉的列不存在。若代码允许视觉折行，可以改 `white-space: pre-wrap; overflow-wrap: anywhere`，但要明确这是对内容呈现方式的另一种选择。

## 七、逻辑属性：跟随文字方向，不重排内容含义

课程页面可能增加阿拉伯语版本。横向书写中，`inline-size` 对应宽度，`block-size` 对应高度；`margin-inline-start` 对应行内起点的外边距，在 LTR 下常是左侧，在 RTL 下常是右侧。逻辑属性将“相对文字流的位置”写出来，避免到处补 left/right 镜像覆盖，详见 [MDN 逻辑属性指南](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Logical_properties_and_values)。

```css
.course-card {
  padding-block: 1rem;
  padding-inline: 1.25rem;
  border-inline-start: 0.25rem solid currentColor;
  text-align: start;
}
.course-card__meta {
  display: flex;
  flex-wrap: wrap;
  gap: 0.5rem 1rem;
}
```

把正确的语言与 `dir="rtl"` 设置在相应文档或区域后，边框起点和对齐会跟随方向。逻辑属性本身不会更改 DOM 中“标题、简介、元信息、阅读入口”的顺序；但书写方向会影响正常的视觉流向，Flex 的 row 起点等也会随之改变。应区分“跟随语言排版方向”和“随意反转语义顺序”。

不要为了让一张桌面截图看起来好看，把手机的阅读入口通过 order 移到标题前面，或在 RTL 模式下无条件加 row-reverse 再反一次。视觉重排可能与键盘焦点和辅助技术的阅读顺序不一致。最稳健的起点是让 DOM 本身就按合理的阅读与操作次序组织；具体导航和无障碍细节见[第四篇](./04-文字媒体与无障碍.md)。

## 八、组合成可解释的课程列表

下面在前一篇结构基础上，给最新课程区域增加列表与筛选区。卡片可以复制多个，标题长度应有变化；它们始终保留同一套语义顺序。

筛选按钮这里只展示布局与状态标记，尚未实现筛选行为；真正实现时应同步内容与 aria-pressed，而不能只更换按钮颜色。网格项目在同一行默认可以拉伸到相近外观高度，但内部正文仍由内容决定，不需要给每张卡片写死高度。

面对 390px 可用宽度，课程变成一列；面对 834px，足够数量的课程按当前最小尺寸形成三列；面对 1440px，容器封顶并形成四列。用户调大根字号时，16rem 的卡片下限也增长，列数可能减少，给更大的文字留出空间。这种变化是内容尺度参与布局的结果。

与之相反，若把 1440px 宽页面写死，再套 `transform: scale(390 / 1440)`，视觉宽度虽然缩小，普通流仍按变换前的尺寸分配空间，文字和点击区域也一起缩小。浏览器没有因此重新换行，也没有重新选择列数。局部图示需要缩放时可以有专门理由，但阅读页面应优先改变内容的排列与尺寸约束，而不是整体缩放站点。

## 九、练习与解释答案

### 练习一：负空间分给谁

容器 600px，两个 Flex 项 basis 为 500px、300px，shrink 分别为 1、2。忽略 gap 和其他盒模型开销，且没有最小尺寸限制，最终各多宽？

答案：负空间为 200px；加权值为 500 与 600，总计 1100。第一项减少 `200 × 500/1100 ≈ 90.91px`，剩 409.09px；第二项减少 `200 × 600/1100 ≈ 109.09px`，剩 190.91px。不是按 shrink 的 1:2 直接减，也不是各减 100px；如果存在内容下限，还需要冻结与重新分配。

### 练习二：给 1fr 加了零为什么仍溢出

网格已经写 `minmax(0, 1fr)`，卡片里仍有一条不换行的很长 URL。能否由此断言 minmax 没生效？

答案：不能。轨道可能已经正确变窄，溢出的是内容自身。检查项目的 min-inline-size、文字的 white-space 和 overflow-wrap；需要阅读的 URL 可以应急换行，代码则可以局部滚动。必须区分轨道宽度、项目宽度和绘制溢出。

### 练习三：少量课程为什么突然变宽

1000px 容器，gap 20px，自动重复最小 240px、最大 1fr，只有两张卡片。auto-fill 和 auto-fit 分别大约多宽？若有五张卡片，auto-fit 的第二行会只剩两条加宽轨道吗？

答案：最多容纳三列。auto-fill 保留空轨道，每列 320px；auto-fit 折叠空轨道，两列各 490px。五张时三条轨道都已被占用，最后一行的空单元格不等于整条空轨道，所以第二行通常仍按三列轨道对齐。

### 练习四：用户字号改变后的布局

根字号调到 20px，视口宽 834px，外层仍是 `min(calc(100% - 2rem), 72rem)`，网格最小列宽 16rem、gap 1rem。卡片足够多时可放几列，每列多宽？

答案：容器宽 `834 - 40 = 794px`，列最小宽 320px、gap 20px。两列至少 660px，三列至少 1000px，所以放两列。每列 `(794 - 20) ÷ 2 = 387px`。不要为了恢复三列把字体缩回去；用户已表达更大文字需求，布局应该给内容更多空间。

### 练习五：组件被放进 230px 侧栏

为什么 `minmax(16rem, 1fr)` 容易失败，而 `minmax(min(100%, 16rem), 1fr)` 更稳健？它能否自动解决内部 1000px 宽代码行？

答案：根字号 16px 时，前者最小列宽 256px，已大于外部 230px；后者允许下限降为 230px。但它只解决轨道本身的最低宽度选择，不能替代码决定换行或滚动。内部内容仍需设置可收缩边界及局部溢出策略。
