# 04｜文字、媒体与无障碍：缩小布局时保留阅读与操作能力

系列导航：[阅读指南](./00-阅读指南.md) · [视口、像素与尺寸基础](./01-视口像素与尺寸基础.md) · [流式布局与内容驱动设计](./02-流式布局与内容驱动设计.md) · [媒体查询与容器查询](./03-媒体查询与容器查询.md) · 本篇 · [移动端、平板与折叠屏](./05-移动端平板与折叠屏.md) · [项目规范、调试与验收](./06-项目规范调试与验收.md)

上一篇让课程卡片能在主列表与侧栏中换结构，本篇处理真正决定可用性的内容：标题是否读得清，封面是否选得对，报名按钮是否点得到，放大后是否还能完成任务。响应式不是把同一张设计稿按比例压缩。空间变少时，应调整排列、留白与信息组织，让用户继续读、继续操作，而不是把内容一起变小。

本文仍以资讯与课程卡片为主线，视口条件示例只使用 768、1024、1440px。所有包含实际媒体地址的位置均使用外部资源变量，例如 `{{courseImageUrl}}`，表示需要使用者提供的真实媒体路径。它们是模板占位符，不是可直接访问的 URL，也不是可直接运行的完整页面。本文不生成图片、不引用外链占位图片、不修改应用 UI，不执行运行测试。

## 一、先确定文字底线，再讨论流式字号

假设一张卡片在 390px 视口里只有约 358px 可用宽度，标题为“从资讯列表到课程侧栏：内容驱动的响应式设计”。如果设计只允许两行，最容易想到的做法是把字号从 20px 降到 12px，让标题勉强塞进去。但用户获得的是更难读的文字；放大之后，它还可能因为固定高度继续被截断。更合理的顺序是允许标题自然换行、让卡片高度增长、把课时与报名操作分行，再考虑摘要是否需要经过明确设计的折叠。

`rem` 适合表达整个界面的字号层级与基础间距，它参照根元素的计算字号。`em` 适合让组件局部尺寸跟随自身文字，例如按钮的左右内边距；用于 font-size 时，em 则按父元素字号计算。这里讨论的是普通样式声明，不能套到上一篇媒体查询条件的特殊字体规则中。

例如根字号 16px、按钮字号 1.125rem，则按钮文字是 18px；若其左右 padding 为 1em，则每侧是 18px。根字号变为 20px 后，文字成为 22.5px，内边距也随之变成 22.5px。这样按钮有机会随字一起长大。若按钮被固定为 32px 高、文本只能一行且 overflow hidden，那么即使使用 rem，仍然会裁切。单位选择只能提供基础，布局约束同样重要。

下面是课程文字区域的完整局部结构与样式，链接锚点需由接入页面提供对应目标：

```html
<article class="reading-card" aria-labelledby="reading-course-title">
  <p class="reading-card__meta">前端实践 · 8 课时</p>
  <h2 id="reading-course-title">
    <a href="#course-detail">从资讯列表到课程侧栏：内容驱动的响应式设计</a>
  </h2>
  <p class="reading-card__summary">
    学会根据可用空间调整内容顺序，让长标题、真实封面和报名操作在放大后依然可用。
  </p>
  <a class="reading-card__action" href="#registration">查看报名说明</a>
</article>
```

```css
.reading-card {

  min-inline-size: 0;
  padding: 1.25rem;
  color: #202124;
  background: #ffffff;
  border: 1px solid #767676;
  border-radius: 0.75rem;
}

.reading-card h2 {
  margin-block: 0.5rem 0.75rem;
  font-size: 1.25rem;
  line-height: 1.4;
  overflow-wrap: anywhere;
}

.reading-card__meta,
.reading-card__summary {
  font-size: 1rem;
  line-height: 1.7;
}

.reading-card__summary {
  max-inline-size: 36em;
  overflow-wrap: anywhere;
}

.reading-card a { color: #123c87; }

.reading-card__action {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  min-block-size: 2.75rem;
  padding: 0.5em 1em;

  outline-offset: 3px;
```

这里没有给正文设固定高度。中文长标题能换行，长网址也可以在必要时断开。行高采用无单位数值，使后代继承的是倍率：1.7 倍行高在 16px 字号时约 27.2px，在 20px 字号时约 34px。若在父级写 `line-height: 24px`，后代标题变大后仍可能继承这个固定长度，造成重叠。无单位行高不是万能规定，但对于多字号内容是较稳妥的起点。

行长也影响可读性。英文排版常以 ch 限制行宽；`1ch` 近似当前字体中数字“0”的前进宽度，并不等于一个汉字的宽度，所以 `max-inline-size: 60ch` 不等于每行 60 个中文字。中文可先用 em 做量级估算，再用真实标点、中英混排和不同字体检查，不能把单位值当成精确字数合同。字距、字体回退、标点挤压都会改变实际行长。

## 二、clamp 的上下界不等于无障碍保证

需要标题在大空间适度增长时，可以用 `font-size: clamp(1.25rem, 1.1rem + 0.6vw, 1.75rem)`。最小值阻止它无止境缩小，最大值阻止它霸占页面，中间值让大小连续变化。默认根字号为 16px 时，390px 视口中的中间值为 `17.6 + 2.34 = 19.94px`，最终被下界限制为 20px；1440px 时中间值为 `17.6 + 8.64 = 26.24px`，低于上界 28px，因此取 26.24px。

为什么不要直接写 4vw？因为纯视口单位让字主要随视口宽度改变，窗口变窄或浏览器缩放触发更窄的 CSS 视口时，字号可能反而下降。加入 rem 是改善，但不是“自动满足 200% 放大”的证明。浏览器整页缩放、仅文字缩放、用户默认字号，以及 clamp 在不同分支间切换，都会影响最终可见大小。

举一个近似演算：宽度 1440px、100% 缩放时，上述公式取 26.24px。假设窗口保持相同物理宽度，200% 页面缩放后 CSS 视口约为 720px，中间值降到 `17.6 + 4.32 = 21.92px`，再乘页面缩放得到约 43.84 的视觉量级，相比起点约增长 1.67 倍，而非机械的两倍。这个演算用于暴露风险，不是声称某个公式在所有浏览器必然失败；实际缩放路径、后续倍率、用户机制与完整布局都需核验。

错误结论是“含 rem 就合规”。正确流程是先提供可读下界，再分别检查文字能否达到要求的放大量、逐级放大过程中有没有内容或功能丢失，以及重排后的布局是否可用。如果流式标题很难验证，保持固定 rem 字号、让结构重排，往往比继续调复杂公式更可靠。尤其不能在窄屏规则里把正文缩小，用这种抵消用户缩放的方式维持构图。

## 三、响应式图片先解决两个不同问题

封面需要响应式，可能是因为同一画面需要不同分辨率，也可能是因为不同区域需要不同裁切。这两个问题不能混为一谈。前者由 srcset 与 sizes 向浏览器提供候选资源，后者通常由 picture 表达画面方向或构图选择。

先定义本文使用的资源变量约定：`{{courseImage480Url}}`、`{{courseImage960Url}}`、`{{courseImage1440Url}}` 分别由外部提供真实宽度为 480、960、1440 像素、内容与比例一致的资源；`{{courseImageUrl}}` 是基础回退资源。变量值可以来自项目已授权本地媒体或实际媒体服务，必须存在且返回正确类型。变量名中的数字是资源元信息要求，不会自动生成相应图片。真实素材若只有一种尺寸，就只提供真实存在的一项，不伪造 srcset 候选。

以下示例是假设封面横跨页面内容区，左右各留 16px，并在 1024px 后限制为 60rem 宽。这个 slot 模型与前面的卡片列表是两个局部场景，不能把它的 sizes 原封不动复制到三列卡片：

```html
<img
  class="course-cover"
  src="{{courseImageUrl}}"
  srcset="{{courseImage480Url}} 480w,
          {{courseImage960Url}} 960w,
          {{courseImage1440Url}} 1440w"
  sizes="(min-width: 1024px) min(60rem, calc(100vw - 2rem)), calc(100vw - 2rem)"
  width="1440"
  height="810"
  alt="课程案例中的资讯列表与侧栏布局对比"
>
```

```css
.course-cover {
  display: block;
  box-sizing: border-box;
  inline-size: calc(100vw - 2rem);
  block-size: auto;
  margin-inline: auto;
}

@media (min-width: 1024px) {
  .course-cover { max-inline-size: 60rem; }
}
```

这是 HTML 模板，替换资源变量且提供真实图片后才能运行。width 与 height 在此假设回退图及同构图候选均为 16:9；若素材比例不同，需填写真实尺寸，不能用示例数字冒充资源事实。CSS 决定最终显示尺寸，sizes 用于告知浏览器预期显示槽位，不能依靠 sizes 替代布局样式。默认字号不是 16px 时，rem 对应的实际长度也会变化，模型仍应与 CSS 保持一致。

## 四、手算一次浏览器选图，才能发现 sizes 的谎报

`480w` 表示资源固有宽度为 480 图像像素，必须与文件真实宽度相符。它不是显示 480 CSS px 的命令。浏览器根据 sizes 的第一个成立条件估计 slot，再将候选宽度除以 slot 得到有效密度，与设备像素比等因素一起决定选择。

以默认根字号 16px、视口 390 CSS px 为例，sizes 选中 `calc(100vw - 2rem)`，slot 为 `390 - 32 = 358 CSS px`。若 DPR 为 2，理想资源宽度约为 `358 × 2 = 716` 图像像素。三个候选有效密度分别约为 `480 / 358 = 1.34x`、`960 / 358 = 2.68x`、`1440 / 358 = 4.02x`。960w 是一个合理的清晰度候选，但不能保证浏览器一定下载它，浏览器还可能考虑缓存、带宽、数据节省策略及实现选择。

到了 1440px 视口，slot 被声明为 60rem，即默认 960 CSS px。DPR 为 1 时，960w 正好对应 1x；DPR 为 2 时，理想目标为 1920 像素，但当前列表只有最大 1440w，因此不存在能完全满足理想密度的候选。正确做法是评估真实素材和网络预算，按需要提供更大且真实存在的版本，而非以为 w 描述符能放大源文件细节。

若把三列卡片的图片也写成 `sizes="100vw"`，浏览器可能按整屏宽度估计，而真实 slot 只有约三分之一屏，造成多余下载。反过来，申报比实际更小的 slot 则可能导致模糊。检查应对比 CSS 中的最终槽位宽度与 sizes 描述，不能只看资源文件名是否带有 small、large。

密度描述符解决的是另一种情况：图片显示槽位本来就固定，只有像素密度变化。例如固定 5rem 宽的课程缩略图，在默认字号下为 80 CSS px，外部提供 80 与 160 像素宽的相同画面：

```html
<img
  class="course-thumb"
  src="{{courseThumb80Url}}"
  srcset="{{courseThumb80Url}} 1x, {{courseThumb160Url}} 2x"
  width="80"
  height="80"
  alt=""
>
```

```css
.course-thumb {
  inline-size: 5rem;
  block-size: auto;
}
```

这里是 x 密度候选，不使用 sizes；同一组 srcset 不应混写 w 与 x。若用户根字号变大，5rem 的槽位也变大，现有最高 2x 资源不一定仍足够清晰，应按真实场景评估，不能把这组示例当作永恒准确的密度映射。空 alt 的前提是缩略图只装饰相邻已充分命名的课程内容；若它承载额外信息，就必须提供合适替代文本。

## 五、picture 处理构图和格式，img 承担最后回退

同一张多人讲座封面在宽布局中能看清整个教室，到了窄卡片中却可能只剩几个小人影。仅提供分辨率更高的版本不会改变主体太小的问题。这时应由内容制作方提供真正不同的裁切，例如宽景与讲师近景，用 picture 进行艺术指导选择。

下面的变量同样需要真实资源注入：Wide 表示宽景，Close 表示近景；每种画面外部提供 AVIF 与 JPEG 版本。示例假设所有版本均为 16:9，以便讲清选择顺序而不混入比例切换：

```html
<picture>
  <source
    media="(min-width: 768px)"
    type="image/avif"
    srcset="{{courseWideAvifUrl}}"
  >
  <source
    media="(min-width: 768px)"
    type="image/jpeg"
    srcset="{{courseWideJpegUrl}}"
  >
  <source type="image/avif" srcset="{{courseCloseAvifUrl}}">
  <img
    class="course-art"
    src="{{courseCloseJpegUrl}}"
    width="960"
    height="540"
    alt="讲师在白板上演示资讯卡片从单列到多列的变化"
  >
</picture>
```

```css
.course-art {
  display: block;
  inline-size: 100%;
  block-size: auto;
}
```

浏览器按顺序寻找 media 与 type 等条件都可用的 source：宽布局优先宽景 AVIF，不支持该格式则可选宽景 JPEG；窄布局可选近景 AVIF，最终由 img 的 JPEG 回退。source 负责选择资源，img 仍不可省略，替代文本放在 img 上。type 是格式能力筛选，不意味着候选文件请求失败时一定自动改选下一项，所以每个地址都必须真实可用。

若真实宽景与近景比例不同，应使空间预留也跟着选中比例调整，可以按实际情况给 source 提供对应 width、height，并核验目标环境行为，或在相同条件下明确设置外层比例。不能继续统一写 960×540，然后期待布局自动知道另一张是竖图。

## 六、尺寸属性、裁切和布局偏移各管一件事

img 上的 width、height 能让浏览器在资源下载前获得固有比例线索。1440×810 对应 16:9，在显示宽度 320px 时就可以预留约 180px 高度。这样后续标题不必等图片下载后突然下移，有助于降低 CLS，即累积布局偏移。它们不是禁止响应式缩放的固定尺寸命令；配合 `inline-size: 100%; block-size: auto`，图片仍可随父级收缩。

`aspect-ratio` 也可用于明确媒体框比例，但要说明你是在创建设计框，还是展示素材真实比例。若强制一个 16:9 框容纳正方形素材，下一步必须决定裁切还是留白。`object-fit: cover` 保持素材比例并填满框，超出部分会被裁掉；`contain` 尽量完整显示内容，可能出现留白。这两者只有在元素显示框与素材比例产生约束时才体现差异。

```css
.course-media-frame {
  aspect-ratio: 16 / 9;
  overflow: hidden;
  background: #f0f2f5;
}

.course-media-frame > img {
  display: block;
  inline-size: 100%;
  block-size: 100%;
  object-fit: cover;
  object-position: 60% 35%;
}

.course-media-frame--diagram > img {
  object-fit: contain;
  object-position: center;
}
```

这里的 60% 35% 是需要针对真实素材调试的焦点位置，不是识别人脸的智能算法。讲师脸部、白板关键内容或图表坐标若被裁掉，不能只因为“填满了框”就交付。照片可按主体设置焦点；课程步骤图、证书、文字图通常更应考虑 contain、提供放大入口或转为可读 HTML。alt 要表达图片在当前上下文中的作用，而非机械写“课程图片”；复杂图表还需要邻近说明或详细替代内容，短 alt 无法承载全部数据。

## 七、视频适配与自动播放没有因果关系

视频的响应式同样是比例、宽度与控制器空间问题，不需要通过 autoplay 才能适配。下面使用真实视频、海报与字幕的外部变量；字幕文件应真实存在并与视频内容匹配：

```html
<video
  class="course-video"
  controls
  playsinline
  preload="metadata"
  poster="{{coursePosterUrl}}"
  width="1280"
  height="720"
>
  <source src="{{courseVideoUrl}}" type="video/mp4">
  <track
    kind="captions"
    src="{{courseCaptionsUrl}}"
    srclang="zh"
    label="中文字幕与音效说明"
    default
  >
  当前浏览器无法播放视频，请阅读下方的课程文字稿。
</video>
<p><a href="#course-transcript">阅读课程文字稿</a></p>
```

```css
.course-video {
  display: block;
  inline-size: 100%;
  block-size: auto;
  aspect-ratio: 16 / 9;
  object-fit: contain;
  background: #000000;
}
```

controls 提供基本播放控制，playsinline 影响部分移动环境中的内联播放体验，二者都不替代适配。若素材不是 16:9，应填写真实尺寸并重新评估显示框。是否自动播放涉及注意力、声音、流量、用户控制和浏览器策略，是另一个设计决策；自动播放被阻止也不应导致课程内容无法访问。字幕、文字稿与必要的音频描述需要根据内容与适用要求提供，响应式 CSS 本身无法补齐媒体无障碍。

## 八、200% 文字放大与 400% 重排是不同检查

WCAG 2.2 的 1.4.4 Resize Text 为 AA：除字幕和文字图像等该条款所述例外外，文字需要能放大至 200%，且不丢失内容或功能。这里关心文字可被有效放大及相关控件仍可用，并不要求只能依靠某一种浏览器按钮实现；也不能因为样式使用 rem 就宣布通过。应检查增量放大过程，而不只是某个终点。

1.4.10 Reflow 同为 AA，关注放大后是否能重排，避免普通内容需要同时横纵滚动。对横向书写的内容，关键基准是相当于 320 CSS px 的宽度；常见验证方式是在初始可用宽度 1280 CSS px 的浏览器内容区保持窗口不变，将页面缩放到 400%，得到约 320 CSS px 的布局视口。这里不是把屏幕硬件宽度当 1280，也不是把任何 400% 环境都一概认为正好 320。

对纵向书写的内容，规范还有相当于 256 CSS px 高度的要求。地图、需要双向布局才能保持意义的数据表等特定内容有例外；例外应局限于确需二维布局的部分，不能借此让整页普通文字都横向溢出。实际控件、浮层和固定栏也要纳入重排检查。

因此需要两份不同记录：一份观察文字是否可达 200% 且无损失，另一份观察 320 CSS px 等效重排时是否仍能阅读、操作。直接把设备模拟器设为 320px 能发现许多布局问题，但不能完全替代真实页面缩放过程中浏览器控件、字体与断点共同作用的检查。两项都不能用“390px 手机预览看起来正常”推导通过。

课程卡片常见失败是正文高度固定、报名条固定在底部遮住最后一行、弹窗使用固定宽度。修正应让正文自然增长，让操作区进入流式布局或为固定区预留真实空间，并让弹窗能在有限空间中滚动。放大后减少装饰可以，删除报名条件和必填错误信息则会损失内容与功能。

## 九、点击目标：分清 AA、AAA 与项目建议

WCAG 2.2 的 2.5.8 Target Size (Minimum) 是 AA，要求指针输入目标至少 24×24 CSS px，但明确包含例外。间距例外的判断不是简单地“任意两按钮间隔 24px”，而是把直径 24 CSS px 的圆放到每个不足尺寸目标的包围盒中心，圆不能与另一个目标，或另一个不足尺寸目标的相应圆相交。

例如两个 16×16px 的方形目标水平相邻，中心间距若是 20px，两只直径 24px 的圆会相交，不能依靠该间距例外；若中心距 28px，则两圆不相交，在没有其他相交目标的前提下，可以满足这一例外条件。这里评估的是实际可点击目标边界，不是图标画出来的线条范围。

该条款还包含等效目标、行内目标、用户代理控制以及必要呈现等例外，需按原文条件判断。正文句子中的普通行内链接，不应机械套成每个字都要有一个独立 24px 方框。例外不是鼓励把所有工具按钮缩小，而是避免破坏文本等合理呈现。

2.5.5 Target Size (Enhanced) 的 44×44 CSS px 是 AAA，并有其自身例外。44 不是所有 AA 页面都必须达到的统一最低数字。项目可以出于触摸舒适度建议主要操作约 44px 或更大，但应标注这是项目设计目标，而非篡改 AA 的要求。前文按钮的 2.75rem 在根字号 16px 时约为 44px；根字号不同会变化，所以它表达相对尺寸策略，不能永远当成固定 44px 的测量结果。

## 十、对比度、焦点与阅读顺序需要一起成立

WCAG 1.4.3 的普通文本最低对比度通常为 4.5:1，大号文本为 3:1。大号不能靠作者主观感觉判断：常用拉丁文字门槛为至少 18pt 普通字，或至少 14pt 粗体，在 96 CSS px 每英寸换算下约为 24px 与 18.67px；CJK 等字体应参考规范对等效大字尺寸的说明，不能直接把所有 19px 中文都归为大字。拿不准时保留 4.5:1 更稳妥。

该条款对附带、不可用控件文本、纯装饰及标识等有特定例外；不要把“辅助信息”误当成“不可用控件”，灰色课时仍然是需要阅读的文字。UI 控件边界和必要图形还有 1.4.11 非文本对比度要求，常涉及与相邻颜色至少 3:1，不能与文本规则混算。背景图上的白字需要覆盖所有实际背景变化，不能只测一块恰好很暗的区域。

键盘用户要能看见焦点，并按可理解顺序到达课程标题、详情、报名。CSS 的 order 或网格定位能改变视觉位置，却通常不会同步改变 DOM 阅读与 Tab 顺序，所以不要让桌面视觉从左到右、键盘却来回跳。先把 DOM 按内容逻辑安排，再让布局增强它。避免给普通元素添加正数 tabindex 去补偿视觉重排。

隐藏也不是单一行为。`display: none` 和 hidden 通常会把内容移出布局及无障碍树；opacity: 0 仅视觉透明，元素可能仍在 Tab 顺序中，造成看不见的焦点。`aria-hidden="true"` 会隐藏辅助技术语义，但并不会自动禁止内部链接获得键盘焦点，不能拿它包住仍可操作的核心按钮。需要保留给读屏用户的补充标签，可使用经过项目验证的 visually-hidden 工具；需要真正禁用整块交互时，要按组件状态管理焦点与可交互性，必要时使用 inert 并核验支持。

弹窗同样不能只做缩小：需要可理解名称、打开后的初始焦点、模态时的背景交互隔离、适当的焦点约束、Escape 等关闭方式以及关闭后返回触发器。正文太长时允许内部滚动，关闭入口不能被挤出视口。可优先使用适合项目的原生 dialog 与 showModal 能力，但仍需验证焦点、命名与业务关闭行为，不能认为换标签就完成全部无障碍。

## 十一、减少动态效果时，功能不能等待动画结束

用户开启 prefers-reduced-motion 可能是为了避免眩晕或注意力干扰。对课程卡片而言，悬停抬升、连续闪动、进场大位移通常不是完成任务的必要部分。可以在偏好成立时去掉位移与过渡，保留清楚的静态反馈：

```css
.motion-card {
  transition: transform 160ms ease, background-color 160ms ease;
}

@media (hover: hover) and (pointer: fine) {
  .motion-card:hover { transform: translateY(-0.125rem); }
}

@media (prefers-reduced-motion: reduce) {
  .motion-card,
  .motion-card:hover {
    transform: none;
    transition: none;
    animation: none;
  }
}
```

错误实现常把“显示报名成功内容”放进 animationend 回调。动画被关闭、被取消、元素提前移除时，这个事件可能不发生，业务状态就永远卡住。修正应先完成业务状态和可访问状态，再把动画作为表现层。以下客户端函数直接展开课程说明，不依赖动画完成：

```html
<button type="button" id="course-more" aria-controls="course-notes" aria-expanded="false">
  展开或收起课程说明
</button>
<div id="course-notes" hidden>
  <p>课程共 8 课时，报名之前请确认学习所需的浏览器与练习时间。</p>
</div>
```

```js
function connectCourseDisclosure(button, panel) {
  const toggle = () => {
    const nextOpen = button.getAttribute("aria-expanded") !== "true";
    button.setAttribute("aria-expanded", String(nextOpen));
    panel.hidden = !nextOpen;
  };

  button.setAttribute("aria-expanded", String(!panel.hidden));
  button.addEventListener("click", toggle);
  return () => button.removeEventListener("click", toggle);
}
```

调用方应提供真实 button、带 id 的 panel，并将按钮 aria-controls 指向该 id；函数在客户端挂载后调用，在销毁时执行返回的清理函数。若还要给展开加动画，应让动画取消或减少动态效果时也能立刻得到同样的展开结果。JS 驱动的非必要运动也应读取 matchMedia 的偏好并处理 change 与卸载清理，不能以为 CSS 的媒体查询会自动停止 JS 定时器或画布循环。

## 十二、练习与参考答案

练习一：根字号 16px，按钮 1.125rem，padding-inline 为 1em，各是多少？如果按钮高度锁为 24px，使用 rem 是否就一定安全？

答案：文字是 18px，每侧内边距是 18px。固定 24px 高可能容不下行高、边框或放大后的文字，所以仍不安全。改成内容撑开和合理 min-block-size，并检查长标签与换行；单位不能抵消错误的高度约束。

练习二：390px 视口，左右各 16px，DPR 为 3，候选是 480w、960w、1440w，理想目标是多少？一定选最大图吗？

答案：slot 为 358 CSS px，理想资源宽约 1074 图像像素。1440w 是高于这个需求的候选，但浏览器选择有缓存、网络与策略因素，不能保证一定选择。先确认 sizes 没谎报，再根据实际画质与传输成本决定资源集合。

练习三：为什么不能把 1280px 宽、400% 缩放的重排结果当作 200% 文字放大的全部证据？

答案：前者主要验证相当于 320 CSS px 宽度下的重排与双向滚动限制，后者验证文字放大及内容功能不丢失。断点和流式字号可能抵消部分视觉放大，两者需要分别记录。模拟器直接设置 320px 可以辅助检查，但不能覆盖全部缩放行为。

练习四：两枚 16×16px 图标按钮的中心距是 20px，可以因为有 4px 空隙就符合 AA 间距例外吗？44px 又是什么？

答案：不可以，直径 24px 的中心圆会相交。44×44 CSS px 是 AAA 增强目标条款的尺寸要求，并非 2.5.8 AA 的统一最低值；项目可以主动采用更舒适的主要目标建议，但需说明层级和例外。

练习五：卡片封面必须填满，图中白板文字却被 cover 裁掉，怎样修正？减少动画后展开失效又应改哪里？

答案：先判断白板文字是否是内容，必要时用 contain、不同构图、放大入口或 HTML 文字说明，而不是继续调 cover 来掩盖丢失。展开失效应检查业务是否只在 animationend 后提交；先独立完成 expanded、hidden 与业务状态，再让可取消动画跟随状态。
