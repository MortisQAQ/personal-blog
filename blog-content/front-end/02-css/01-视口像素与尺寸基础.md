# 01｜视口、像素与尺寸基础：浏览器究竟在计算什么

[返回阅读指南](./00-阅读指南.md) · [下一篇：流式布局与内容驱动设计](./02-流式布局与内容驱动设计.md)

本系列围绕一个“课程资讯列表”页面展开：页面有站点标题、筛选区、课程卡片，每张卡片包含标题、简介、分类和阅读入口。我们的目标是让同一份内容在窄手机、平板和桌面上都能阅读，而不是把某张设计稿按比例压进屏幕。

这一篇先解决尺寸的参照物。看到 `width: 50%`，要能追问“谁的百分之五十”；看到手机宣传页上的分辨率，要知道它为什么不能直接拿来写 CSS；看到文字变大，要分辨是字体设置、页面缩放还是双指缩放。只有参照物明确，后面的布局计算才有意义。

本文所有演算若未特别说明，假设横向书写、没有额外滚动条占宽，根字号为用户常见默认值 `16px`。这是便于计算的条件，不是要求把根字号锁死为 16px。`390 / 834 / 1440` 是系列使用的观察宽度；仓库中的 `768 / 1024 / 1440px` 是本地断点约定，均不是 Web 的全球设备分类标准。后文需要视口断点时沿用这些值，本篇本身无需媒体查询。

## 一、先分清“排版的格子”与“屏幕发光的格子”

假设一张课程卡片写了 `width: 300px`。这里的 `px` 是 **CSS 像素**，浏览器用它描述布局坐标和尺寸；它不是“必须点亮屏幕上的 300 个物理像素”。物理像素是显示面板上的实际采样点，设备像素比 DPR 描述两套尺度之间的关系。

在不考虑双指缩放、显示缩放等额外复杂因素的简化模型里：

```text
一个方向上的设备像素数 ≈ CSS 像素数 × devicePixelRatio
300 CSS px × DPR 3 ≈ 900 个设备像素
```

因此，DPR 为 3 的手机可以用更多物理像素描绘同样的字形边缘，让文字更细腻。它不意味着作者必须把字号乘以 3。`font-size: 16px` 仍然是在 CSS 坐标中排版为 16px；具体映射由浏览器和显示系统完成。[MDN 对 devicePixelRatio 的定义](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)同时说明，它会受到页面缩放影响，不能永远当作一块屏幕固定不变的硬件标签。

如果某设备在特定显示模式下有 1170 个横向物理像素，DPR 为 3，那么 `1170 ÷ 3 = 390` 可以帮助理解其常见逻辑宽度。但这个除法需要对应相同方向、相同显示模式和缩放状态，不能仅凭产品海报上的分辨率推导任意浏览器窗口宽度。桌面上还有系统缩放、窗口大小和浏览器边栏；移动端还有方向切换、多窗口和浏览器界面。CSS 像素也不保证在所有设备上对应相同的毫米长度。

把分辨率当布局宽度的错误写法是：

```css
/* 错误思路：因为手机宣传分辨率是 1170，就做 1170 宽的页面 */
.course-page {
  width: 1170px;
}
```

在 390 CSS px 的可用空间中，它会产生约三倍宽的布局，而不是自动变成一张清晰的手机页面。正确方向是让容器响应可用空间：

```css
.course-page {
  width: min(calc(100% - 2rem), 72rem);
  margin-inline: auto;
}
```

这里没有手机型号名单。只要设备提供相同的 CSS 可用宽度，布局计算就有相近结果；DPR 的主要关联转向图片清晰度、画布采样等问题，而不是替普通卡片再写一套宽度。媒体清晰度继续见[文字、媒体与无障碍](./04-文字媒体与无障碍.md)。

## 二、布局视口与视觉视口为什么要分开

想象先在一张大纸上排好课程列表，再通过一个可移动的窗口看其中一部分。用于排版的参考区域对应布局视口；用户此刻真正看到的区域对应视觉视口。两者在初始状态可能接近，但发生缩放或软键盘出现后就不一定相同。

布局视口影响根级布局和通常的宽度媒体查询。视觉视口则描述当前可见部分的大小与位置。手机双指放大后，页面中的标题和卡片通常不会为了缩小的可见区域重新排成另一套列数，而是原布局被放大，用户可以平移观看。[MDN 的视口概念指南](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/CSSOM_view/Viewport_concepts)用这一区分解释缩放时的差异。

在开发者工具控制台中，可以只读观察：

```js
console.table({
  layoutClientWidth: document.documentElement.clientWidth,
  innerWidth: window.innerWidth,
  visualWidth: window.visualViewport?.width,
  visualScale: window.visualViewport?.scale,
  dpr: window.devicePixelRatio,
});
```

`clientWidth` 与 `innerWidth` 在滚动条处理上可能不同；这段代码用于对照现象，不用于通过数值猜测手机型号。`visualViewport` 也不能替代所有布局逻辑。比如软键盘是否调整布局视口、视觉视口或覆盖内容，受浏览器、平台与配置影响，不能笼统认定“键盘弹出就会触发所有高度单位变化”。

### viewport meta 设置的是浏览器起始排版条件

为了兼容早期桌面网页，移动浏览器在缺少合适设置时可能采用接近桌面宽度的虚拟布局视口，再把结果缩小显示。常见描述中的约 980px 只是历史实现的典型数值，不是所有浏览器必须采用的规范常量。此时卡片确实排下了，字却小到难以阅读。

课程列表的 HTML 头部应该包含：

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

`width=device-width` 让初始布局视口宽度与设备提供的逻辑宽度配合；`initial-scale=1` 指定初始缩放比例。这里的 device-width 不是要求作者使用物理分辨率。它也不自动修复子元素的 `width: 1170px`：meta 先让浏览器使用合适的排版条件，作者仍要提供能适应该条件的布局。详见 [MDN viewport meta](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)。

不要为了“布局稳定”附加 `user-scalable=no` 或用 `maximum-scale=1` 禁止放大。依靠放大阅读的用户需要缩放，某些浏览器即使忽略这些限制，也不构成作者设置限制的理由。正确的稳定性来自内容能换行、组件能增长，而不是让用户迁就一个固定尺寸。

### 页面缩放与双指缩放：同样变大，不同计算

假设桌面浏览器的内容区域宽度在 100% 页面缩放时相当于 1200 CSS px。用户把页面缩放设为 150%，若窗口的显示面积不变，布局可用宽度就约为 `1200 ÷ 1.5 = 800 CSS px`。这会改变布局条件，可能触发宽度媒体查询，让原来的三列变成两列；通常还会改变 `devicePixelRatio`。

换成手机：初始布局宽度 390 CSS px，用户双指放大到 2 倍。忽略浏览器界面细节，视觉视口宽度约为 `390 ÷ 2 = 195 CSS px`，布局视口通常仍约为 390 CSS px。双指缩放通常不改变 `devicePixelRatio`，额外放大可以通过视觉视口的 scale 观察。把 `CSS 尺寸 × DPR` 当作双指缩放后屏幕占用尺寸的完整公式就不准确了，因为还存在视觉放大这一步。

以上是帮助理解的模型，浏览器实际数值会受滚动条、舍入和平台影响。要记住的因果关系是：页面缩放通常改变排版可用的 CSS 尺度；双指缩放通常放大已经形成的布局。不要把两者统一写成“浏览器重新给所有元素乘一个 transform”。

## 三、百分比不是单位换算表，而是对包含块提出问题

绝大多数课程卡片位于普通文档流中。此时其包含块通常来自最近的块容器祖先的内容区域，而不是简单等于“最近一个 DOM 父元素”。定位元素、变换祖先等会带来其他规则，完整边界见 [MDN 包含块指南](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Display/Containing_block)。本节先限定普通流，避免把不同格式化上下文混在一起。

假设列表区域的内容宽度为 800px，卡片写 `width: 50%`，其指定宽度是 400px。把页面拖宽不一定直接改变卡片：如果列表已经被 `max-width` 限制住，包含块宽度没有变化，50% 的结果也不变。嵌套容器才是很多“明明窗口一样大，组件却不一样宽”的原因。

还要问：400px 对应盒子的哪一层？

```css
/* content-box 下，width 只约束内容区 */
.course-card {
  width: 50%;
  padding: 16px;
  border: 2px solid;
}
```

若容器为 800px，卡片的边框盒宽度是 `400 + 16 × 2 + 2 × 2 = 436px`。两张卡片即使没有 gap，也已经需要 872px。不能因为 width 相加恰好为 100%，就断定一定排得下。

```css
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

使用 `border-box` 后，400px 包含内容、padding 和 border，内容区变成 `400 - 32 - 4 = 364px`。margin 仍然在外面，gap 也不会被这条规则消除。两张 50% 卡片再加 16px gap，仍需 816px；这种情况应交给下一篇的 Grid 或 Flex 分配空间。`box-sizing` 的作用是统一尺寸口径，而不是免除空间预算。

### 为什么 height: 100% 经常没有想象中的效果

宽度通常能从包含块得到确定值，高度却经常由内容反向撑开。如果父级 `height: auto`，子级又要求“父级高度的 100%”，双方就形成循环依赖。在普通非绝对定位块布局中，包含块高度依赖内容时，子元素的百分比高度通常按 auto 处理；不能看到最终父级有 600px 高，就认为百分比一定回算成 600px。[MDN height](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/height)列出了这一前提。

```css
/* 错误预期：以为子元素会占满浏览器高度 */
.course-list { height: auto; }
.course-card { height: 100%; }

/* 确实需要最小一屏的页面外壳，可由视口给出独立依据 */
.course-page { min-height: 100svh; }

/* 课程卡片本身通常应由内容决定高度 */
.course-card { height: auto; }
```

若某个演示容器明确 `height: 400px`，其普通子元素 `height: 50%` 就可以得到 200px；但长简介可能超出这个高度。因此“能计算”不等于“适合内容”。Flex、Grid 在确定尺寸方面有专门规则，不能拿普通流结论覆盖所有场景。

另一个反直觉之处是：在常见横向书写的普通块布局中，`padding-top: 10%` 的百分比通常也取包含块的宽度作参照，而不是高度。800px 宽容器中得到 80px。这是属性定义造成的，不能凭“top 是竖向”猜基准；如今表达媒体比例通常直接用 `aspect-ratio` 更清楚。

## 四、rem 和 em：先找到字号，再算其他尺寸

`rem` 参照根元素的计算字号；`em` 在 `font-size` 上参照父级字号，在 padding 等属性上参照元素自己的计算字号。这一区别有明确的求值次序，[MDN 的值与单位教程](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Values_and_units)对此给出了嵌套演示。

```css
html { font-size: 100%; }
body { margin: 0; font-size: 1rem; line-height: 1.6; }
.course-card { font-size: 1.25em; padding: 1em; }
.course-card__tag { font-size: 0.8em; padding: 0.5em 1em; }
```

根字号为 16px、body 字号为 16px 时：

```text
卡片字号 = 父级 16 × 1.25 = 20px
卡片 padding = 自己的 20 × 1 = 20px
标签字号 = 父级 20 × 0.8 = 16px
标签上下 padding = 自己的 16 × 0.5 = 8px
标签左右 padding = 自己的 16 × 1 = 16px
```

因此不能把卡片的 `padding: 1em` 也算成父级的 16px。同一个 em 的基准因属性不同而不同，先求出自身字号才能继续算内边距。嵌套字号也可能连乘：每层都用 `1.25em`，三层之后是 `16 × 1.25³ = 31.25px`。不希望跟随组件字号的全局间距，可以选择 rem；希望按钮内边距随按钮文字一起增长，em 则很有用。

### 保留用户根字号，才能让相对尺寸有正确起点

上例中的 `html { font-size: 100%; }` 也可以直接省略，让浏览器与用户设置决定根字号。假设用户默认字号为 20px，`1rem` 就应以这个起点计算。不要为了方便心算普遍设置 `html { font-size: 10px; }`，也不要把 `62.5%` 当作无代价的必选项；后一种虽然仍是比例，却把默认正文起点缩小，后续所有尺寸都要补偿。

尤其不要把全站根字号绑定为 `视口宽度 ÷ 设计稿宽度`：例如 1440px 设计稿对应 16px 根字，在 390px 视口按比例就只有 `16 × 390 ÷ 1440 ≈ 4.33px`。此时所有 rem 文本、间距、点击区域都会一起缩小，布局看似装进屏幕，用户却失去了可读性。应该让列数、换行和空间分配适应窄屏，正文保留合理字号。`rem` 是参照根字号的工具，不是“自动适配”开关。

## 五、vw、vh、svh、dvh：参照区域的状态也重要

`1vw` 是视口参考宽度的 1%。在 390px 宽视口中，`10vw = 39px`；在 1440px 中则是 144px。它适合需要明确随视口变化的尺寸，但若给列表内卡片写 `width: 80vw`，即使卡片被放入 300px 宽侧栏，它仍然可能根据整个视口得到上千像素。组件内部通常更适合百分比或布局分配。

高度还受到移动浏览器地址栏伸缩影响。现代视口单位区分小视口、大视口与动态视口：[MDN length](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length)给出了这些单位的定义与注意事项。

假设某手机浏览器界面展开时可用高度为 700px，收起时为 800px。在这个简化场景中：

- `100svh` 以较小状态为参照，约为 700px，浏览器栏收起后仍保持这个基准。
- `100lvh` 以较大状态为参照，约为 800px；现代常见实现中的 `100vh` 等价于这一大视口口径。
- `100dvh` 随动态界面状态调整，可能在 700px 到 800px 之间变化，过程中更新策略由浏览器实现决定。

所以课程列表若只是希望“短内容时也至少铺满首屏”，可以用 `min-height: 100svh`，允许长内容继续增长。确实需要贴合当前可用区域的阅读面板才考虑 `dvh`，并评估滚动中尺寸变化。不要把所有卡片高度都设为 `100dvh`，也不要假定 `dvh` 必然扣除软键盘高度或直接等于双指缩放后的视觉视口高度。

## 六、min、max、clamp：把布局意图写成可计算的边界

回到课程页面容器：我们希望窄屏左右各留 1rem，宽屏内容不要无限增长。这个要求先转换为两条候选宽度，再取更小值：

```css
.course-page {
  width: min(calc(100% - 2rem), 72rem);
  margin-inline: auto;
}
```

在根字号 16px、父级可用宽度等于观察宽度、容器自身没有额外 padding 和 border 时，`2rem = 32px`、`72rem = 1152px`：

| 可用宽度 | 扣除两侧间距 | 取 min 后的宽度 | 左右各自剩余 |
| --- | --- | --- | --- |
| 390px | 358px | 358px | 16px |
| 834px | 802px | 802px | 16px |
| 1440px | 1408px | 1152px | 144px |

这里的 100% 来自包含块，rem 来自根字号，两者可以在 `calc()` 中先换算到可比较的尺度。`calc(100%-2rem)` 缺少减号两边的必要空白，不能当作推荐写法；应写 `calc(100% - 2rem)`。

`min()` 是选择较小值，不代表“最小宽度”；`max()` 是选择较大值，也不代表“最大宽度”。例如 `padding: max(1rem, 2vw)`，390px 时在 16px 与 7.8px 中选 16px，1440px 时在 16px 与 28.8px 中选 28.8px。它表达的是“内边距至少有 1rem”。

`clamp()` 再增加一个首选值，正常上下界关系下可按下面的式子计算：

```text
clamp(下界, 首选值, 上界) = max(下界, min(首选值, 上界))
```

```css
.course-page__title {
  font-size: clamp(1.5rem, calc(1rem + 2vw), 3rem);
  line-height: 1.2;
}
```

根字号为 16px 时，下界 24px、上界 48px。390px 视口的首选值是 `16 + 7.8 = 23.8px`，最终选 24px；834px 时首选值为 `16 + 16.68 = 32.68px`，保持该值；1440px 时为 `16 + 28.8 = 44.8px`，也在边界内。到 1920px 时首选值 54.4px，就限制为 48px。这一宽度只是演算输入，不是新增媒体查询断点。

与纯 `font-size: 4vw` 相比，rem 边界和混合首选值给文字保留了与用户字号设置的联系。但“用了 clamp”不自动保证缩放可访问性：放大页面同时可能减少 CSS 视口宽度，使 vw 项反向减小，需要实际检查 200% 缩放和文字放大后的可读性、遮挡与功能。详见 [MDN clamp 的无障碍说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/clamp)，后续在第四篇继续讨论。

## 七、把这一篇落到同一张页面上

以下只是教材片段，不要求新建 HTML 文件。结构保留真实内容的阅读顺序，布局先从单列开始：

```html
<main class="course-page">
  <h1 class="course-page__title">前端课程与资讯</h1>
  <p>从浏览器尺寸计算开始，逐步搭建稳健的阅读页面。</p>
  <section aria-labelledby="latest-heading">
    <h2 id="latest-heading">最新课程</h2>
    <article class="course-card">
      <h3><a href="/courses/responsive">理解响应式布局的尺寸依据</a></h3>
      <p>解释视口、字号与内容空间之间的关系。</p>
      <span class="course-card__tag">CSS 基础</span>
    </article>
  </section>
</main>
```

```css
*, *::before, *::after { box-sizing: border-box; }
html { font-size: 100%; }
body { margin: 0; font-family: sans-serif; line-height: 1.6; }
.course-page {
  width: min(calc(100% - 2rem), 72rem);
  margin-inline: auto;
  min-height: 100svh;
  padding-block: 2rem;
}
.course-page__title {
  font-size: clamp(1.5rem, calc(1rem + 2vw), 3rem);
  line-height: 1.2;
}
.course-card { padding: 1rem; border: 1px solid currentColor; }
.course-card__tag { font-size: 1rem; padding: 0.25em 0.5em; }
```

此时不同手机会根据自身 CSS 可用宽度得到不同容器宽度，文字按字号和行宽自然换行。它们不需要共享相同的物理分辨率；也不需要每种机型拥有一份 CSS。屏幕变窄时内容高度增加，这是正常排版结果。下一篇再让卡片根据可用空间形成多列。

## 八、练习与解释答案

### 练习一：像素与缩放

某设备初始布局宽度 390 CSS px、DPR 为 3。一条 100 CSS px 宽的横线，在未双指缩放的简化模型中对应多少设备像素？双指放大 2 倍后，应不应该把 CSS 宽度手动改成 50px？

答案：初始约为 `100 × 3 = 300` 个设备像素。无需修改 CSS 宽度，双指缩放由浏览器放大显示；手动缩回会抵消用户意图。此时可见区域变小，DPR 通常仍为 3，不能据此断言视觉显示完全没变化。

### 练习二：盒模型预算

父级内容宽 600px，卡片 `width: 50%`、左右 padding 各 20px、左右 border 各 1px。content-box 与 border-box 下各多宽？若两张并排加 16px gap，border-box 是否足够？

答案：content-box 的边框盒宽为 `300 + 40 + 2 = 342px`；border-box 为 300px，内容区 258px。两张 border-box 卡片加 gap 仍为 616px，因此不够。问题出在轨道预算，应由布局系统扣除 gap 后分配，而不是再盲目减少字体。

### 练习三：em 的基准

父级字号 20px，按钮写 `font-size: 0.9em; padding: 0.5em 1em`。最终字号和内边距是多少？若 padding 改为 1rem，根字号为 16px，又是多少？

答案：字号 `20 × 0.9 = 18px`，上下 padding 为 9px、左右为 18px。改为 `padding: 1rem` 后四边均为 16px，因为它改用根字号，不再跟随按钮自己的字号。

### 练习四：用户设置与容器

用户根字号为 20px，包含块宽 834px。`width: min(calc(100% - 2rem), 72rem)` 是多少？如果误把根字号固定为 16px，会抹去什么差异？

答案：`2rem = 40px`，`72rem = 1440px`，取 `min(794px, 1440px) = 794px`。固定根字号会使布局和字体的 rem 尺度失去这项用户偏好带来的变化。允许容器最大宽度随文字起点增长，是保留阅读容量的一种合理结果，不应自动视为设计错误。
