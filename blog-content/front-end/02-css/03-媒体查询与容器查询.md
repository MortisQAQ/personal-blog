# 03｜媒体查询与容器查询：让变化发生在真正缺空间的地方

系列导航：[阅读指南](./00-阅读指南.md) · [视口、像素与尺寸基础](./01-视口像素与尺寸基础.md) · [流式布局与内容驱动设计](./02-流式布局与内容驱动设计.md) · 本篇 · [文字、媒体与无障碍](./04-文字媒体与无障碍.md) · [移动端、平板与折叠屏](./05-移动端平板与折叠屏.md) · [项目规范、调试与验收](./06-项目规范调试与验收.md)

本文延续前两篇的资讯与课程卡片：卡片包含分类、标题、摘要、课时和报名入口，既能出现在课程主列表，也能进入文章侧栏。我们要回答的不是“手机应该用哪个断点”，而是“哪一层缺少空间，以及改变结构需要什么条件”。这决定了查询应该观察视口还是容器，也决定了代码应该交给 CSS 还是 JavaScript。

本文是独立教材，不修改应用。视口宽度示例统一使用本项目登记的 768、1024、1440px。后文的 `36em` 是讲解容器阈值的通用示例，不能据此推断项目已经允许该阈值；落地前应核对并登记项目容器查询规范。文中代码展示完整局部结构，但不代表已接入当前应用或通过浏览器验收。

## 一、先算内容需要多少宽度，再选择断点

假设课程卡片在两列状态下，每张至少需要 20rem 才能舒服地容纳中文标题和两个操作，两列间距需要 1.5rem，页面左右各留 1rem。以初始字号 16px 为演算前提，总宽度需求是 `2 × 320 + 24 + 2 × 16 = 696px`。这不是让你立刻增加一个 696px 断点，而是说明两列布局在这个量级以下会开始紧张。实际还要代入更长标题、价格、放大后的文字与本地化标签，不能只量设计稿中的短句。

本项目只登记了 768、1024、1440px，因此可以让列表在 768px 开始尝试两列，并检验 768 附近是否仍留有余量。若需求计算得到最小可用宽度超过 768px，应先减少装饰性占位、改变操作排列或继续保持一列；确需新规则时走规范登记，不能随手写一个设备型号对应的值。内容驱动的意思是有证据地改变结构，并不意味着允许在同一项目中无限增加断点。

在 390px 视口中，左右各 16px 后内容区约 358px，一列卡片容易成立。在 834px 中内容区约 802px，两列加 24px 间距后，每张约 389px。在 1440px 中，若主区域外框限制在 72rem，即默认字号下的 1152px，扣去左右各 16px 内边距及两个 24px 列间距，每张约为 `(1152 - 32 - 48) / 3 ≈ 357.3px`。可以看到，大屏中的卡片未必比平板中的宽：视口更大可能换来更多列，而非每个组件都变大。这正是后面需要容器查询的原因。

不要把“768以上”解释成平板身份。桌面用户把窗口拖窄、页面被嵌入分屏、浏览器放大后 CSS 视口变窄，都可能进入同一个布局状态。媒体查询表达的是当时环境，不是用户属于哪一类设备。

## 二、宽度条件必须能解释每一个边界

`@media (width: 768px)` 表示视口宽度恰好等于 768 CSS px，不能覆盖“从这里开始”的全部情况。`@media (min-width: 768px)` 才表示大于或等于 768px；`max-width` 同样包含等号。宽度并不总是整数，缩放和布局环境可能产生小数值，因此不该用 `767px` 或 `767.98px` 猜测另一侧边界。

支持范围语法的环境可以直接写出互斥区间：

```css
@media (width < 768px) {
  .course-list { --layout-name: narrow; }
}

@media (768px <= width < 1024px) {
  .course-list { --layout-name: medium; }
}

@media (1024px <= width < 1440px) {
  .course-list { --layout-name: wide; }
}

@media (width >= 1440px) {
  .course-list { --layout-name: expanded; }
}
```

这里用自定义属性标识状态，目的是展示区间归属；它本身不会生成布局。宽度 767.999px 归第一段，768px 只归第二段，1024px 只归第三段，1440px 只归第四段，没有交叠，也没有空白。相反，同时写 `max-width: 768px` 与 `min-width: 768px` 会在边界双双命中；若双方都改同一属性，结果依赖层叠，维护者容易误判。

区间互斥并非所有场景都必须采用。移动优先通常有意让 `min-width` 条件累积：宽度 1440px 时，768、1024、1440 三条规则全部成立，再由层叠形成最终结果。你必须区分“需要唯一分类的区间”与“需要逐步增强的样式”，不能把后者的重叠当成错误，也不能拿后者为前者的边界歧义开脱。

## 三、移动优先是一种层叠组织方式

先写所有宽度都能使用的单列结构，再在空间足够时增加列。这样，不认识某个增强语法的浏览器也有可用基础。以下局部示例不涉及图片资源，标题和链接都可直接替换为业务内容：

```html
<section class="course-section" aria-labelledby="course-heading">
  <h2 id="course-heading">近期课程与资讯</h2>
  <div class="course-list">
    <article class="course-card">
      <p class="course-card__category">前端实践</p>
      <h3><a href="#course-details">从资讯列表理解响应式布局</a></h3>
      <p>同一张课程卡片进入主列表与侧栏，如何保持阅读顺序和操作可达？</p>
      <div class="course-card__actions">
        <span>共 8 课时</span>
        <a href="#registration">查看报名说明</a>
      </div>
    </article>
  </div>
</section>
```

```css
* { box-sizing: border-box; }

.course-section {
  inline-size: min(100%, 72rem);
  margin-inline: auto;
  padding-inline: 1rem;
}

.course-list {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  gap: 1.5rem;
}

.course-card {
  min-inline-size: 0;
  padding: 1.25rem;
  border: 1px solid #767676;
  border-radius: 0.75rem;
  overflow-wrap: anywhere;
}

.course-card h3 {
  margin-block: 0 0.75rem;
  font-size: 1.25rem;
  line-height: 1.4;
}

.course-card p { line-height: 1.7; }

.course-card__actions {
  display: flex;
  flex-wrap: wrap;
  align-items: center;
  gap: 0.75rem 1rem;
}

@media (min-width: 768px) {
  .course-list { grid-template-columns: repeat(2, minmax(0, 1fr)); }
}

@media (min-width: 1024px) {
  .course-card { padding: 1.5rem; }
}

@media (min-width: 1440px) {
  .course-list { grid-template-columns: repeat(3, minmax(0, 1fr)); }
}
```

这段代码在 834px 时使用两列；1024px 以后仍是两列，只增加卡片内边距；1440px 时才覆盖列数为三列。这样安排来自内容密度，而非“每到一个断点都必须换列数”。后写规则能覆盖前写规则的前提是其他层叠因素相当；`!important`、层、选择器优先级都可能改变结果，不能笼统地说“媒体查询写后面就一定赢”。

常见错误是基础样式先写三列，再用多个小屏规则逐个清除固定宽度、定位和高度。遗漏一项就会留下溢出。更可靠的修正是把基础结构改成自然换行和内容撑高，把真正需要空间的增强留到 `min-width` 中。这并不要求先设计手机稿，而是要求最基础的阅读与操作不依赖大画布。

## 四、媒体查询中的 em、rem 不读取作者的根字号

普通声明里的 `rem` 以根元素字号为参照；媒体查询条件中的字体相对单位有特殊规则：`em` 和 `rem` 按初始字体大小解释，而非读取作者给 `html` 设置的字号。这能避免“查询成立后改根字号，根字号又改变查询是否成立”的循环依赖。

假设浏览器初始字体大小是 16px，则媒体查询条件中的 48em 和 48rem 都对应 768px。即使作者写 `html { font-size: 20px; }`，这个条件也不会因此变成 960px；但普通声明中的 `padding: 1rem` 会随根字号成为 20px。如果用户把浏览器默认字体偏好设为 20px，初始字体参照可能随之改变，此时 48em 才可能对应 960px。初始大小并非永远固定为 16px，16 只是常见演算前提。

因此，不能先把根字号改成 62.5%，再把媒体查询里的 em 当成 10px 计算；也不能把媒体查询中的 rem 与稍后容器查询中的 em 混为一谈。本篇视口代码仍统一采用登记的 px 值，以上换算仅用于讲清语义，不能直接扩散成新的项目断点。

## 五、宽屏不代表鼠标，粗指针不代表手机

`hover` 描述主要指点设备是否能方便地悬停；`pointer` 描述主要指点设备的精度，可匹配 `none`、`coarse`、`fine`。`any-hover` 和 `any-pointer` 观察所有可用指点设备的能力集合。带触屏的笔记本可以同时拥有粗指针和精细指针，平板也可能接鼠标，鼠标还可能在页面打开后才连接。`any-pointer: coarse` 与 `any-pointer: fine` 因而可能同时成立。

即使 `any-hover: hover` 成立，也只说明某个可用设备能悬停，不证明用户此刻就在使用它，更不证明键盘用户能触发悬停。以下增强只增加视觉反馈，报名入口始终可见：

```css
.course-card__actions a {
  display: inline-flex;
  align-items: center;
  min-block-size: 2.75rem;
  padding-inline: 0.75rem;
  color: #123c87;
  text-decoration: underline;
}

.course-card a:focus-visible {
  outline: 3px solid #174ea6;
  outline-offset: 3px;
}

@media (hover: hover) and (pointer: fine) {
  .course-card__actions a:hover {
    background: #eaf1ff;
  }
}

@media (any-pointer: coarse) {
  .course-card__actions { gap: 1rem; }
}
```

错误做法是默认 `opacity: 0` 隐藏报名按钮，只在 `:hover` 显示，再把手机当作特殊例外补丁。修正应当反过来：核心操作基础态就存在，键盘、触摸、鼠标、辅助技术都可访问；悬停仅提供额外提示。若摘要被折叠，应由真实按钮控制展开并维护 `aria-expanded`，不能让重要内容只有鼠标移入才能发现。输入能力查询也无法检测所有辅助技术，更不能代替语义化 HTML。

## 六、容器查询解决“同屏不同宽”的卡片问题

现在把同一张卡片放到 1440px 页面中的两个位置：主区某个推荐位宽 680px，侧栏宽 280px。媒体查询看到的都是同一个视口，若它命令所有卡片横向排列，侧栏就会被挤坏。真正需要观察的是每张卡片分到的局部空间。

先由外层槽位建立查询容器，再让内层卡片根据槽位宽度变化。下面用文本区代表媒体介绍，不需要下载图片：

```html
<div class="course-slot">
  <article class="local-card">
    <div class="local-card__intro">响应式布局 · 8 课时</div>
    <div class="local-card__body">
      <h3>一张卡片如何进入不同页面区域</h3>
      <p>空间不足时顺序阅读，空间足够时将介绍与正文并排。</p>
      <a href="#course-syllabus">查看完整课程大纲</a>
    </div>
  </article>
</div>
```

```css
.course-slot { min-inline-size: 0; }

.local-card {
  display: grid;
  grid-template-columns: minmax(0, 1fr);
  gap: 1rem;
  padding: 1rem;
  border: 1px solid #767676;
}

.local-card > * { min-inline-size: 0; }
.local-card__body { overflow-wrap: anywhere; }
.local-card h3 { font-size: 1.25rem; line-height: 1.4; }
.local-card p { line-height: 1.7; }

@supports (container-type: inline-size) {
  .course-slot {
    container-type: inline-size;
    container-name: course-slot;
  }

  @container course-slot (inline-size >= 36em) {
    .local-card {
      grid-template-columns: minmax(0, 2fr) minmax(0, 3fr);
      align-items: start;
    }
  }
}
```

`inline-size` 按书写方向观察行向尺寸；在常见横排中文中相当于宽度。采用行向尺寸容器能查询这个方向，同时通常仍允许块方向高度由内容自然撑开。不要为了“什么都能查”随便换成 `size`，双轴尺寸包含会带来不同的尺寸计算约束，可能让依赖内容高度的容器表现异常。

此处 `36em` 按相关查询容器的计算字号解释。若该容器字号为 16px，阈值为 576px；字号为 20px，阈值为 720px。它与媒体查询中按初始字体解释的 em 不同。选择 36em 是为了演示标题、文本和间距一起需要多大空间，属于通用教材阈值，落入本项目之前仍要登记规则，不能当成项目规范的隐含豁免。

`@supports` 负责检查所需声明能力，再启用增强。没有相应能力时，浏览器保留基础纵向卡片；核心链接和内容没有丢失。它不是对所有容器查询子功能的统一认证：尺寸查询、样式查询、滚动状态查询以及具体语法应分别核对兼容信息。本文不写未经确认的浏览器版本号，发布时应查文末 MDN 的兼容表，并在项目目标环境验证实际使用的语法。

## 七、祖先选择、命名和“不能查询自己”

尺寸查询为要应用样式的元素寻找合适的祖先查询容器。无名称时通常选择最近且支持所需轴的祖先；写名称后，会沿祖先链寻找名称及能力符合要求的容器。因此，容器名称限制的是向上寻找的对象，并非普通 CSS 选择器的全局分组。

假设页面结构是 `page-shell → course-slot → local-card → action-slot → button`，其中 page-shell 和 course-slot 都建立了容器，而 action-slot 又是一个更近的行向尺寸容器。针对 button 的匿名查询可能读取 action-slot，而 `@container course-slot (...)` 会继续向上找到课程槽位。命名能让嵌套组件表达“我关心外层卡片空间”，减少无意中查询到新包装层的风险。若嵌套层使用相同名称，则最近的合格同名祖先仍会接管，应有意设计名称与作用域。

容易误写的是给 `.local-card` 自己建立容器，然后期望下面这条规则读取它自身宽度：

```css
/* 错误预期：这不会读取 local-card 自己的容器尺寸。 */
.local-card { container-type: inline-size; }
@container (inline-size >= 36em) {
  .local-card { padding: 3rem; }
}
```

对于规则选中的 local-card，查询会寻找它的合格祖先；若不存在，条件不会按作者想象的自身尺寸成立；若外层恰好有容器，读到的反而是外层。正确修正就是上一节的包装槽位：course-slot 是容器，local-card 是被改变的后代。这样不会因为卡片刚改变内边距就反过来决定自己是否应该改变内边距，查询设计避免了这类自触发循环。

容器的尺寸也需要页面布局分配。若槽位在 Flex 子项中因最小内容宽度拒绝收缩，光加查询并不能治好溢出；仍需检查 `min-inline-size: 0`、网格轨道、长字符串和父级宽度。容器查询选择何时换结构，不会替你补齐所有布局约束。

## 八、cqi 是长度，不是“自动安全”的字体方案

`1cqi` 等于相应合格查询容器行向尺寸的 1%。容器宽 600px 时，2cqi 是 12px；宽 300px 时，2cqi 是 6px。它适合做有限的空间联动，例如在卡片后代上写 `padding: clamp(1rem, 3cqi, 2rem)`，既随局部空间变化，又有上下界。注意这里的 cqi 也要寻找合格容器，不会因为写在某元素上就自动参照该元素自身。

如果没有合适的容器，容器查询长度单位会退回相应轴的小视口单位，cqi 对应小视口行向单位 svi。于是把组件从有容器的主区搬到忘记建立容器的侧栏，长度可能突然按整个小视口计算，而不是报错或变成零。嵌套时，命名的 `@container` 也不意味着其中所有 cqi 自动绑定该名字；长度单位仍按自身规则寻找合格容器，附近新增的容器可能改变它的参照。

因此应把“需要哪个祖先提供尺寸”作为组件使用契约，检查包装层，并用 clamp 保留合理边界。用于字体时还要继承下一篇的放大验证：把 rem 加进公式并不能自动证明满足文字放大要求。不要用 `font-size: 2cqi` 让侧栏正文缩到几个像素。

## 九、什么时候才需要 JavaScript 查询

改列数、内边距、卡片方向应优先用 CSS。只有当行为确实需要知道条件变化，例如在进入宽布局时启用可选的课程键盘预览，才需要 JavaScript。`innerWidth` 是读取当下宽度的一个数值；它不会自动订阅变化。绑定 resize 后每次窗口调整都重新计算则会产生大量回调，还容易让 JS 和 CSS 维护两套不同边界。

`matchMedia` 接受媒体查询字符串，`matches` 给出当前结果，`change` 在结果跨边界变化时通知。不要漏掉首次同步，否则只有用户第一次跨断点后功能才生效。下面的函数接收业务回调，返回解除订阅函数：

```js
function observeWideLayout(onChange) {
  if (typeof window === "undefined") {
    return () => {};
  }

  const query = window.matchMedia("(min-width: 1024px)");
  const notify = () => onChange(query.matches);
  query.addEventListener("change", notify);
  notify();

  return () => {
    query.removeEventListener("change", notify);
  };
}

// 在客户端挂载完成后调用；页面或组件销毁时调用 stop。
const stop = observeWideLayout((isWide) => {
  // 将结果传给可选行为，不以此隐藏核心报名入口。
  document.documentElement.dataset.coursePreview = isWide ? "wide" : "base";
});
// 宿主生命周期结束时执行 stop()。
```

这里没有调用 stop 是因为独立片段没有定义宿主销毁时机；接入 React 时应在 effect 中订阅并返回 stop，在其他框架也要放进对应卸载钩子。不要用两个看起来相同的匿名箭头分别 add 和 remove，它们是不同函数，清理不会成功。需要连续像素值去计算画布时，resize 或 ResizeObserver 才可能更合适，后者观察元素尺寸，而非机械地把所有场景替换成 matchMedia。

服务端渲染还有额外约束：服务端没有 window，也不知道用户实际 CSS 视口。仅加 `typeof window` 防报错不等于解决水合。若服务端输出单列 DOM，客户端第一次 render 就依据 matches 输出完全不同的节点，仍可能水合不一致。稳妥策略是服务端与客户端首轮都输出同一份语义结构，用 CSS 控制布局；客户端挂载后再启动不影响核心可达性的增强。必须以媒体状态驱动渲染时，应提供一致的服务端快照或明确的挂载后状态转换，而不是猜测设备类型。隐藏整页等待测宽也会损失内容稳定性和首屏体验。

## 十、练习与参考答案

练习一：768px 恰好同时命中 `max-width: 768px` 与 `min-width: 768px`，这是浏览器错误吗？把页面状态改成四段，要求不存在小数宽度漏洞。

答案：不是错误，两种旧语法都包含等号。需要唯一状态时用 `width < 768px`、`768px <= width < 1024px`、`1024px <= width < 1440px`、`width >= 1440px`。若只是移动优先累积增强，则只写递增 min-width，并让层叠承担覆盖，不必伪造互斥。

练习二：1440px 的页面里，主推荐槽位宽 680px，侧栏宽 280px。容器字体为 16px，36em 时卡片横排，哪个横排？作者把 html 字号设为 20px 后一定有什么结果？

答案：最初阈值 576px，680px 横排，280px 纵排。根字号变化后，应检查查询容器最终计算字号；如果它继承到 20px，阈值变成 720px，两者都纵排；若容器自身固定为 16px，阈值不变。不能把“根变了”直接等同于所有容器字体都变了。

练习三：用户在触屏笔记本上连接鼠标，any-hover 成立。可以把报名操作默认藏起来吗？

答案：不可以。该条件不代表用户当前输入方式，更没有涵盖键盘。操作应基础态可见并有语义，hover 只增加反馈。用 Tab、Enter、触摸点击分别检查可达性，不用设备名字替代验证。

练习四：一个组件卸载后仍收到媒体变化回调，另一个组件首屏水合警告。分别先查什么？

答案：前者检查是否使用同一个函数引用移除 change 监听，是否实际在卸载时调用清理；后者检查服务端和客户端首次渲染是否由不同的媒体结果生成不同 DOM。把订阅放到挂载后可以处理浏览器能力访问，但首轮 DOM 一致性仍需单独保证。
