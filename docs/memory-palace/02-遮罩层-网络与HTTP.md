## 二、真实画面与八股知识点的深度串联（7 大定桩）

### 桩位 1：全屏白底画布 ➔ 从 URL 输入到请求发出的全流程

- **真实画面**：
  整个视口被 `#f8f8f5` 的纯净白底遮盖，空无一物，仅在等待远端资源到来。
- **宫殿假想联想**：
  你站在白茫茫的门厅前，地址栏像是一张发射台，一串 URL 输进去后，白屏下方开始地动山摇——
- **八股核心考点**（对应题库：`docs/Browser/从url输入到返回请求的过程.md`）：
  1. **URL 解析**：判断是搜索关键字还是合法 URL；协议（https）、主机名（domain）、端口、路径、参数合成。
  2. **DNS 域名解析**（按顺序递归/迭代查询）：
     - 浏览器 DNS 缓存 ➔ 操作系统 hosts 文件 / 本地 DNS 缓存 ➔ 本地路由 DNS ➔ 本地运营商递归 DNS（Local DNS）➔ 根域名服务器（.）➔ 顶级域名服务器（.com）➔ 权威域名服务器。
     - *真实代码印证*：你在 HTML 顶部看到的 `<link rel="preconnect" href="https://cdn.jsdmirror.com">`，就是在向 Local DNS 抢跑。
  3. **获取 IP 与端口**：拿到远端服务器公网 IP，准备向操作系统网络栈递交套接字请求。
- **记忆口诀**：**白底无一物，递归找 IP**。

### 补给单元：为什么“吃葱少女”总是第一个到？（资源发现瀑布）

> 这一节不占桩位号，但它解释了整套遮罩设计存在的全部理由。

#### 1. 第一次请求永远只有一份东西：HTML 主文档

DNS 解析完、TCP 建好、TLS 换完锁之后，浏览器发出的**第一个也是唯一一个**请求是 `GET /`。
此刻浏览器对这个站一无所知：它不知道这里有 React、有几张图、有没有字体、有没有视频。
**其余所有资源，都是 HTML 到达并被解析之后才被“发现”的。**

| 发现时刻 | 资源 | 由谁触发 | 是否阻塞渲染 |
| --- | --- | --- | --- |
| 解析 `<head>` | 字体 ×2（SmileySans / Oswald） | `<link rel="preload" as="font" fetchpriority="high">` | 否（已提权并行加载，不再阻塞遮罩） |
| 解析 `<head>` | 与 CDN 的 TCP/TLS 连接（**这不是资源**） | `<link rel="preconnect" href="https://cdn.jsdmirror.com">` | 否 |
| 解析 `<body>` | `loading-chicong.webp`（约 712KB，跨域 CDN） | `<img class="loading-image" src="…">` | 否 |
| 解析 `<body>` 末尾 | `main.tsx` 及其依赖（整个 React bundle） | `<script type="module" src="/src/main.tsx">` | 否（`type="module"` 天生 defer） |
| **JS 执行之后** | `home/home.webp`、`home/hls/index.m3u8`、`init.mp4`、`segment_000.m4s`、`content/index.json` | React 渲染时才创建 `<video>` / 才发 `fetch` | 否，但它们**此刻才出生** |

再往后的资源基本都不是首屏的：`music/bgm.mp3`（点了才放）、`information/background.webp`（切到介绍页才要）、`vendor/vditor/**`（进写作台才拉）。
它们属于“路由/交互触发”，连发现时机都由用户行为决定。

#### 2. 结论：遮罩不是“下载最快”，而是“根本不用下载”

三个原因叠在一起，才让它抢在所有人前面：

1. **它不需要额外请求。** 遮罩的 DOM 结构和全部 CSS（约 4KB `<style>`）直接内联在 `index.html` 字节流里。HTML 头几个字节一到，`#f8f8f5` 的白底就能画出来——**零网络往返**。
   反例：如果样式写成 `<link rel="stylesheet">`，CSS 属于**阻塞渲染资源**，浏览器必须等它下载并解析完才敢画，白屏会硬生生多出一个 RTT。
2. **文字比图片先到，而且图片不挡路。** `<img>` 是异步的替换元素，未加载完不会阻止文本与背景绘制。所以「少 女 吃 葱 中」这五个字（纯文本 + 内联样式）几乎与 HTML 同时成画，而那张 712KB 的动图是“迟到”的——它到了就显示，没到就是空位，但绝不拖住第一帧。
   这一帧就是 **FCP（First Contentful Paint）**：用户第一次看到“有东西了”。
3. **浏览器只按“发现顺序 + 提示”排队，不按重要性排队。** 在解析到 `<script>` 之前，浏览器压根不知道这个站是 React 应用。React 再重要，也只能排在 HTML 后面——因为 HTML 是所有资源的唯一入口。

#### 3. 真实时间线（打开本站的一瞬间）

```text
T0  回车 → DNS → TCP → TLS → GET /            视口全白，什么都没有
T1  TTFB：HTML 前几个字节到达 → 解析 <style>    白底样式就位
T2  解析到 #global-loading 结构                 白底 + 五字标题成画 = FCP
T3  loading-chicong.webp 返回                   初音落地，开始吃葱（不阻塞任何东西）
T4  main.tsx 及依赖下载并执行                    React 运行时启动
T5  Home 挂载 → 请求 home.webp / hls / index.json   真正首屏的资源此刻才开始下
T6  路由页面挂载且首帧绘制完成               撤遮罩，露出早已画好的首屏；字体 / 视频继续加载
```

#### 4. 反推：为什么它不能做成 React 组件？

如果把遮罩写成 `<AppLoading />`，它就必须等 **bundle 下载完 + React 执行完 + 组件渲染完** 才能出现在屏幕上。
那这段时间屏幕是纯白的——正好是我们想消灭的那段“白屏空隙”。

所以它被刻意写成 `index.html` 里的静态标记，并由 `AppBootstrap` 用裸 DOM（`classList.add` + `remove()`）拆掉，彻底绕开 React。

**一句话收口：把首屏第一帧所需的一切，塞进 HTML 的前几个字节里。** 这就是关键渲染路径（Critical Rendering Path）在工程上的实战版。

### 桩位 2：手里握着的大葱 ➔ TCP 三次握手与四次挥手

- **真实画面**：
  右下角初音紧握着一根鲜绿色的长葱，正前方咬下去分出清晰的段落。
- **宫殿假想联想**：
  葱是一根“网络握手天线”。连接建立时，两人各递三段葱；关闭连接时，两人必须来回扔四次葱头。
- **八股核心考点**（对应题库：`docs/HTTP/三次握手和四次挥手.md`、`docs/CSBasic/TCP的那些事儿.md`）：
  0. **先把三个字母认下来（TCP 标志位）**：
     - **SYN** = Synchronize（同步）➔ **我想建立连接**，顺手把自己的初始序列号 ISN 报过去。
     - **ACK** = Acknowledgement（确认）➔ **你的我收到了**，`ack=x+1` 表示“x 及以前全收到，下一个给我 x+1”。
     - **FIN** = Finish（结束）➔ **我这边没数据了，申请断开**。
     - 一句话：**SYN 建、ACK 收、FIN 断**。
  1. **三次握手（建立连接）**：
     - ① 客户端发 **SYN**（seq=x，进入 SYN_SENT）：*“我要咬一口（能听见吗）？”*
     - ② 服务端回 **SYN + ACK**（seq=y, ack=x+1，进入 SYN_RCVD）：*“收到你咬，我也准备咬（能听见，你呢）？”*
     - ③ 客户端回 **ACK**（seq=x+1, ack=y+1，进入 ESTABLISHED）：*“收到，开吃！”*
     - *为什么不能是两次？* 防止历史失效的连接请求突然传到服务端，造成服务端单方面空等、资源浪费；且双方必须互相同步序列号（ISN）。
  2. **四次挥手（断开连接）**：
     - ① 客户端发 **FIN**（进入 FIN_WAIT_1）：*“我吃饱了，不吃了。”*
     - ② 服务端回 **ACK**（进入 CLOSE_WAIT，客户端进 FIN_WAIT_2）：*“知道你吃饱了，但我可能还有残渣没吐完。”*（半关闭）
     - ③ 服务端发 **FIN**（进入 LAST_ACK）：*“我也擦完嘴了，关门。”*
     - ④ 客户端回 **ACK**，进入 **TIME_WAIT（等待 2MSL）**：防止最后的 ACK 丢失让服务端重传 FIN，并保证网络中旧报文全部消亡。
- **记忆口诀**：**三口建立握手，四口挥泪擦嘴，末尾苦等 2MSL**。

### 桩位 3：呼吸的「Now Loading...」 ➔ HTTP 历史版本演进

- **真实画面**：
  文字一明一暗呼吸（1.5 秒周期），三个小圆点像数据包一样在跳动。
- **宫殿假想联想**：
  随着呼吸节奏加快，初音吃葱的速度经历了四个时代，从“吃一口歇一下”进化到“嚼碎多条并行吞”。
- **八股核心考点**（对应题库：`docs/HTTP/HTTP历史.md`）：
  1. **HTTP/1.0**：短连接。每个请求都得重新 TCP 三次握手，传输完立即断开，没有 Host 头。
  2. **HTTP/1.1**：
     - 引入 `keep-alive`（默认持久连接，连接复用）。
     - 支持管道化（Pipeline），但响应必须按请求顺序返回，存在**队头阻塞（HOL Blocking）**。
     - 增加 Host 虚拟主机、Range 断点续传、强/协商缓存头。
  3. **HTTP/2**：
     - **二进制分帧**（将文本协议改为 Header 帧与 Data 帧）。
     - **多路复用（Multiplexing）**：一个 TCP 连接上并发双向传输多个流，彻底解决应用层队头阻塞（但 TCP 丢包重传仍会有传输层队头阻塞）。
     - **头部压缩（HPACK）**：静态/动态字典避免重复发送巨大 Header。
     - **服务器推送（Server Push）**。
  4. **HTTP/3（QUIC）**：
     - 抛弃 TCP，底层基于 **UDP** 实现 QUIC 协议。
     - 彻底消除 TCP 丢包造成的传输层队头阻塞；支持 **0-RTT** 极速建连；连接迁移（按 Connection ID，切 Wi-Fi/4G 不断连）。
- **记忆口诀**：**1.0 短短断，1.1 管道排队慢，2.0 二进制帧多路转，3.0 跑在 UDP 上不见单**。

### 桩位 4：五字错落大标「少女吃葱中」 ➔ HTTP 状态码五大门派

- **真实画面**：
  五个大字贴在一起，但高低大小各不同：
  - 「**少**」（大，浮起）➔ **1xx**
  - 「**女**」（小，贴底）➔ **2xx**
  - 「**吃**」（大，浮起）➔ **3xx**
  - 「**葱**」（大，贴底）➔ **4xx**
  - 「**中**」（小，贴底）➔ **5xx**
- **宫殿假想联想**：
  这五个字就是五大状态码家族，看高低神态一眼识别：
- **八股核心考点**（对应题库：`docs/HTTP/HTTP状态码.md`）：
  1. **「少」（1xx 协议处理中）**：
     - `101 Switching Protocols`：协议升级（如 HTTP 升级为 WebSocket）。
  2. **「女」（2xx 成功美滋滋）**：
     - `200 OK`：成功拿到资源。
     - `204 No Content`：成功但响应无 Body（打点上报常见）。
     - `206 Partial Content`：范围请求（视频分片加载常见）。
  3. **「吃」（3xx 重定向去别家吃）**：
     - `301 Moved Permanently`：永久重定向（搜索引擎权重转移，浏览器强缓存）。
     - `302 Found`：临时重定向。
     - `304 Not Modified`：命中协商缓存，资源没变，去本地找（极其核心！）。
  4. **「葱」（4xx 客户端自己葱头葱脑报错）**：
     - `400 Bad Request`：请求参数格式错误。
     - `401 Unauthorized`：未登录 / 未提供有效凭证。
     - `403 Forbidden`：已登录但无权限访问该资源。
     - `404 Not Found`：找不到资源。
  5. **「中」（5xx 服务端暴毙中招）**：
     - `500 Internal Server Error`：服务端内部代码跑崩了。
     - `502 Bad Gateway`：网关上游服务器挂了（如 Nginx 找不到 Node）。
     - `503 Service Unavailable`：超载或停机维护。
     - `504 Gateway Timeout`：网关请求上游超时。
- **记忆口诀**：**1 转换，2 成功，3 重定向找缓存，4 客户端找抽，5 服务端倒霉**。

### 桩位 5：4px 初音绿底座线 ➔ HTTP 报文结构与请求方法

- **真实画面**：
  大标题下方有一根非常明显的 4px 纯色实线（`border-bottom: 4px solid #68e0d1`），把上方的大标题和下方的副标严格隔开。
- **宫殿假想联想**：
  这根线就是报文里的**CRLF 空行**！上层是信封头，下层是信件内容，中间全靠这一道绿线阻隔。
- **八股核心考点**（对应题库：`docs/HTTP/HTTP报文组成.md`）：
  1. **请求报文结构**：
     - **请求行**：`Method + Request-URI + HTTP-Version`（例如 `GET /index.html HTTP/1.1`）
     - **请求头（Headers）**：`Host`、`User-Agent`、`Accept`、`Cookie` 等键值对。
     - **空行（CRLF，\r\n）**：*就是这根 4px 绿线*，通知服务器头部结束！
     - **请求体（Body）**：POST/PUT 携带的数据。
  2. **响应报文结构**：
     - **状态行**：`HTTP-Version + Status-Code + Reason-Phrase`（例如 `HTTP/1.1 200 OK`）
     - **响应头**：`Content-Type`、`Set-Cookie`、`Cache-Control` 等。
     - **空行（CRLF）**
     - **响应体**：HTML 源码、图片二进制或 JSON 数据。
  3. **GET vs POST 核心区别**：
     - 语义：GET 是幂等只读获取，POST 是非幂等提交。
     - 传参位置：GET 参数拼接在 URL 路径查询串，POST 放在 Body 中（支持更大容量与多种 Content-Type）。
     - 缓存与书签：GET 会被浏览器主动缓存、加入书签历史，POST 默认不会。
- **记忆口诀**：**起始行开路，头部键值对，绿线隔空行，实体在腹中**。

### 桩位 6：双重贴纸立体投影 ➔ HTTPS 与 TLS 安全加密

- **真实画面**：
  标题字不是扁平的，而是有**纯黑色描边 + 青绿色实阴影 + 模糊黑柔阴影**（三层贴纸装甲，非常牢固）。
- **宫殿假想联想**：
  双重阴影和描边是初音给报文穿上的“防弹衣”，防止路上被偷看或被偷换。
- **八股核心考点**（对应题库：`docs/HTTP/HTTPS.md`）：
  1. **HTTPS 解决的问题**：防窃听（加密）、防篡改（完整性校验）、防冒充（身份认证）。
  2. **混合加密机制**：
     - **非对称加密**：在 TLS 握手阶段使用（RSA 或 ECDHE），耗性能但安全，专门用来商量并交换一个“对称密钥”。
     - **对称加密**：在后续实际传输数据时使用（AES 或 ChaCha20），计算速度极快。
  3. **CA 证书与数字签名**：
     - 服务端把公钥提交给 CA 机构认证。
     - CA 用自己的私钥对服务器信息和公钥进行数字签名。
     - 浏览器内置受信任的根 CA 公钥，解开签名验证证书是否合法（防中间人攻击 MITM）。
  4. **TLS 1.2 握手流程**：
     - Client Hello（支持的协议版本、加密套件、随机数 R1）
     - Server Hello（确认套件、随机数 R2、CA 证书）
     - 客户端验证证书，生成随机数 Pre-master，用证书公钥加密送给服务端
     - 双方结合 R1 + R2 + Pre-master 计算出会话对称密钥，后续通信全加密。
- **记忆口诀**：**非对称来换锁钥，对称加密跑通道，CA 签名防调包**。

### 桩位 7：页面就绪门阀与淡出揭开 ➔ HTTP 缓存机制（强缓存与协商缓存）

- **真实画面与代码**：
  `AppBootstrap.tsx` 里的加载守卫逻辑：
  ```ts
  const PAGE_READY_TIMEOUT = 10_000 // 仅兜底：页面漏发就绪信号时避免遮罩永久停留
  waitForPageReady(PAGE_READY_TIMEOUT).then(() => {
    loadingEl.classList.add('is-hidden') // 0.5s 淡出
    setTimeout(() => loadingEl.remove(), 500)
  })
  ```
- **宫殿假想联想**：
  遮罩层不再等字体或视频（它们已提权并行加载），只等当前路由页面完成首帧渲染；10 秒闹钟只是防止页面漏发信号的兜底。页面一就绪，遮罩立刻淡出（0.5s），字体/视频到了再在页面内渐显——这正是浏览器缓存命中时「本地已有效、无需等待」的极速体验！
- **八股核心考点**（对应题库：`docs/HTTP/HTTP缓存.md`）：
  1. **第一关：强缓存（不问服务器，直接拿本地）**：
     - 优先级：`Cache-Control: max-age=xxx` 优先于 `Expires`（绝对时间受客户端本地时钟影响）。
     - `Cache-Control` 常见指令：
       - `no-store`：绝不缓存任何内容。
       - `no-cache`：可以存，但每次使用必须去服务器走协商缓存验证！
       - `public` / `private` / `immutable`。
     - 状态码表现：`200 OK (from disk cache / from memory cache)`。
  2. **第二关：协商缓存（强缓存失效，带上凭据去问服务器）**：
     - 服务器响应给客户端的标记：
       - `ETag`（内容文件唯一 Hash，精度高） ➔ 客户端下次带 `If-None-Match`
       - `Last-Modified`（最后修改时间，精度到秒） ➔ 客户端下次带 `If-Modified-Since`
     - 比较结果：
       - **内容没变**：服务器返回 **304 Not Modified**（无响应体），客户端立即用本地缓存 ➔ *遮罩光速消失！*
       - **内容已变**：服务器返回 **200 OK** 并携带最新资源。
- **记忆口诀**：**先看 max-age 强不强，再拿 ETag 问店家，没改 304 快速开，变了 200 重新搬**。
