# Project Dossier

把“查得到实现”和“讲得清项目”分开。技术实现概要保存指定快照的实现；母档解释背景、本人动作、技术判断和结果。两者互链，不把两个不同颗粒度的正文拼成一份。

## 入口与产物

先定位已有文档、源码与本人范围。只问影响事实归属且无法从材料确认的信息；允许保留缺口继续。多个项目逐个建档，相关工程能力可作副线，不把团队所有实现归到本人名下。

默认在用户指定目录或当前项目的 `project-dossiers/<项目名>/` 生成中文 Markdown：

| 文件 | 职责 |
|---|---|
| `技术实现概要.md` | 文件树与职责、数据契约、关键实现复刻、状态与异常路径、实现局限 |
| `母档.md` | 七段式叙述：背景目标、职责边界、最难问题、决策与备选、结果证据、复盘改进、可能被追问 |
| `简历.md`（按需） | 2–3 条有依据的贡献，核验备注与可投递正文分离 |
| `面试套件.md`（按需） | 3 分钟主叙述、逐层追问与回答要点、练习反馈 |

默认新建项目档案只交付前两份。只要面试稿或简历时，补最小事实缺口即可，不强制源码归档。

## 母档七段式（固定结构）

母档按以下顺序组织，七段都要有；确实无内容的写明“无”及原因，不留空标题、不用推演填充。章节目的见[母档结构](assets/dossier-template.md)。

1. 背景与目标　2. 个人职责和边界　3. 最难的问题　4. 关键技术决策及备选方案
5. 结果与证据　6. 失败、复盘和后续改进　7. 可能被追问的问题

第 3 章讲问题怎么解决，第 4 章讲为什么选这条路而不是别的；只有具备独立判断价值的决策才在第 4 章单列，否则并入第 3 章。

## 母档派生三种材料

母档是唯一事实源，三种派生物只做压缩与重组，不新增事实、不改变角色与证据边界：

| 材料 | 产物 | 从母档取什么 |
|---|---|---|
| 简历 | `简历.md` | 第 2、3、5 章 → 2–3 条有证据的项目描述 |
| 面试 | `面试套件.md` | 第 1–6 章 → 3 分钟主叙述；第 7 章 → 逐层追问题库 |
| 长期档案 | 母档 + 技术实现概要 + 附录 | 第 4、6 章即完整决策过程与复盘，**不再另建一份重复文件** |

长期档案不是第三个文件：母档第 4 章保留决策过程、第 6 章保留复盘与能力变化，与技术实现概要及必要附录合起来即构成长期档案。派生物之间冲突时以母档为准。

两份主文档都在正文写完后直接结束，不追加收尾维护章节。`来源与核验`、`旧事实覆盖迁移`、`缺口与验收` 及其改名后的等价物（`核验记录`、`附录：来源`、`维护信息` 等），连同集中的源码锚点表、旧事实 ID 对照、独立验收记录和缺口矩阵，都属于交付说明、技能评估记录或任务回复，不写入 `技术实现概要.md` 或 `母档.md`。

区分的办法是问这段内容服务谁：帮读者理解系统的留在正文，帮维护者追溯文档怎么写出来的移出去。版本与读取范围在开头一次说清；源码路径就近放在它解释的模块旁；影响某条主张的证据边界，紧跟那条主张写一句。这样读者在需要时就能看到，不必翻到文末查表。

已有命名优先。旧单份母档先备份，再按内容所有权迁移；保留原事实 ID 或迁移对照到维护记录，不复制已发现的错误。文件不超过 500 行；长实现按模块拆附录，不能靠删掉关键分支缩短。内部材料只留在用户获准的位置，不随技能或投递正文分发。

## 按需工作流

只读当前任务需要的流程。新双档按 1 → 2 → 3 执行；派生与复盘只加载相关阶段。

| 阶段 | 必读文件 | 完成条件 |
|---|---|---|
| 1. 提取事实 | [事实与还原](workflows/01-extract.md) | 快照、结构、契约和关键分支可追溯 |
| 2. 选择故事 | [故事与归属](workflows/02-highlights.md) | 少数有依据的判断，个人动作与团队机制分开 |
| 3. 编写双档 | [双档交付](workflows/03-dossier.md)、[还原结构](assets/reconstruction-template.md)、[母档结构](assets/dossier-template.md)、[写作范例](references/writing.md) | 还原稿能复刻，母档能线性读懂且支持深挖 |
| 4. 简历 | [派生简历](workflows/04-resume.md) | 简短可投递，角色、状态、数字不变形 |
| 5. 面试 | [面试与回填](workflows/05-interview.md) | 自然叙述、三层追问、反馈可回填 |

只要求体检就报告问题与位置，不擅自重写。无源码可以出有边界的草稿，不编文件树或声称完整还原。来源链接是目录时只追相关项目；风格参考不是项目事实。技能维护再读[研究取舍](references/sources.md)与[评估场景](references/evaluation.md)。

## 事实边界

- 当前实现以源码及相应契约为准；历史方案、当时决策以当时记录为准。两者冲突标明版本和证据，不自动替历史找理由。
- 代码存在、本人完成、已上线、有效果是四个不同主张。`已落地` 只表示实现已核实，不自动具备简历资格。
- 保留 `已落地`、`已识别·未落地`、`设计意图`；证据不足写 `待核验`，不等于没实现。标签放索引或必要结论旁，不刷满正文。
- 测试、旧母档和 AI 起草稿都是待交叉核对的材料，不因写了“通过”就当作真相。代码中的保护只证明实际覆盖的写入与生命周期，不外推“彻底解决”。
- 不编本人动作、历史备选、排查过程、数字、上线或改进完成情况。现在回看的方案明确标注，未确认的贡献不进入第一人称口述或简历。
- 缺字段时如实记录现有行为，不替代码补默认业务文本、跳转或兼容逻辑。历史代码已有兜底也不能抹掉或写成推荐实践。
- 指标分别记录 PRD 目标、文档报告值、本次复测值。缺口径的报告值保留并限制使用，不改写成“无数据”；相关性不写成个人优化的因果收益。

## 交付前检查

| 维度 | 检查 |
|---|---|
| 还原 | 仅持还原稿及附录能写出核心伪代码，走通正常和异常输入，再与源码核对 |
| 叙述 | 母档开头能回答“做什么、我做哪部分、难在哪、结果到哪”，不先读快照大表 |
| 深度 | 核心故事能解释约束、机制、取舍及验证，三层追问不是“详见代码” |
| 一致 | 实现细节只在还原稿维护；角色、历史、结果只在母档维护；派生物引用相同事实 |
| 表达 | 因果写段落，并列才列表，对比才表格；代码标识只用于必须精确定位的地方 |
| 收尾 | 正文写完直接结束，无 `来源与核验` / `缺口与验收` / `旧事实迁移` 类章节及其改名等价物，且无指向它们的悬空引用 |

具备子代理能力且获准时，使用未参与写作的读者分别验收；否则明确是自查。正文的列表密度、长项、强调次数只作噪声预警，不是事实正确性或可读性的替代评分。

## 常见偏差

- “母档必须详细所以每个机制填七条”：细节去还原稿；核心机制展开，其余按职责归类，不等长复读模板。
- “加一页摘要就能保留原混排正文”：摘要不能代替分离所有权，两份文档各自形成完整阅读路径。
- “STAR 就要四个加粗列表”：它是完整性检查，不是强制文风；用自然段交代因果。
- “删反引号就降噪”：将无必要的符号换成业务中文，不把标识符墙换成普通字体。
- “代码核验就能写我主导”：贡献依据单独核对，不默认统计 Git 作者或提交量。

`writing-like-lofisu` 仅作可选表达增强。母档本身已须解释架构判断，不是最低层功能清单；使用相邻技能时仍不得改变角色、时态和证据边界。
