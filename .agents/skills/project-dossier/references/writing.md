# 同一事实，两种写法

母档供人线性阅读，还原稿供后来重建。不是给同一篇文章加摘要，而是分别组织信息。下例为教学案例，不是用户经历。

## 已知材料

用户确认自己负责搜索列表的乱序覆盖修复。源码每次搜索递增实例内版本，成功与失败写回前比较版本；没有取消网络。已有 A 先发、B 后发且先完成的用例记录，执行结果未提供，也没有线上性能数据。

## 还原稿的写法

### 搜索响应只允许最新请求写入

代码锚点：`src/search.ts` 的 `createSearch` 及其返回的 `search`。每个列表创建自己的搜索实例，版本初值为 0；输入是关键词，副作用是更新该列表的结果或错误。

每次搜索先递增版本并记录到本次请求。成功与失败回调都检查版本，因此旧请求既不能覆盖新列表，也不能用迟到错误把成功结果改成错误态。

下面是该局部机制的等价伪代码，省略视图与请求包装；未包含卸载保护，不可据此推断卸载行为。

```ts
function createSearch(fetchResults, setResults, setError) {
  let version = 0;
  return async function search(keyword) {
    const requestVersion = ++version;
    try {
      const result = await fetchResults(keyword);
      if (requestVersion !== version) return;
      setResults(result);
    } catch (error) {
      if (requestVersion !== version) return;
      setError(error);
    }
  };
}
```

A 先发、B 后发且先完成时，B 写入结果；A 迟到成功或失败都不更新状态。如果 B 失败，A 也不会成为补偿结果。这是“最新请求优先”，不是“最新成功结果优先”。它不减少请求数量，也没有释放网络资源。

## 母档的写法

### 切换很快时，列表仍应对应最后一次选择

搜索列表的问题不是请求失败，而是结果可能以不同顺序返回。用户已经换了关键词，旧请求却后到，页面就会显示过时内容。我负责的是修复这类覆盖问题，而不是重做搜索服务。

实现时，我让每次搜索带上递增版本，并在成功和失败写回前都检查是否仍是最新请求。只检查成功分支不够：旧请求的报错同样可能覆盖已经成功的新列表。

从源码静态走查，旧响应会在写回前被拦截；已有乱序用例，但执行结果还需要核验。这个处理没有取消在途网络，也没有线上性能收益的测量。现在回看，如果还要降低网络成本，需要另行评估请求取消；那是后续方案，不是本次已完成的工作。

实现细节见还原稿中的“搜索响应只允许最新请求写入”。母档无需重复状态变量名和每条回调。

## 写作检查

因果、转折、权衡用段落，每段推进一个判断；只有真正并列且独立的项才用列表。比较字段、状态或选项时用表格，不把整段推理塞进单元格。

开头先回答项目是什么和本人做什么，不用大快照表阻断阅读。关键链路可以用图或短文本，但不为装饰画图。

代码标识只保留跨系统契约、必须精确定位的符号与必要的例子；其它位置用自然中文。加粗仅用于少数结论，不给每条句子贴加粗标签。长列表项优先重写，不只换行。

角色边界在开头交代，具体归属和验证限制只在有关结论旁补充，不反复用免责句打断故事。文档制作过程、迁移对照和评估步骤放维护记录；母档保留简短来源索引与影响面试的缺口。

参考材料可以借叙事次序与信息组织，不照抄全部格式或其未经核验的主张。紧凑技术稿仍要保留实际边界，不能以可读性为由删掉关键异常分支。
