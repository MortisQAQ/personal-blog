# 阶段 1：提取事实

输入：源码或已有材料、本人范围。输出：`技术实现概要.md` 的事实底稿。背景、个人动作与结果证据留给母档；来源清单、迁移对照和验收缺口留给交付说明或技能评估记录，不另造需要长期同步的事实库。

## 1. 固定版本与范围

记录仓库或材料名、模块路径、分支/提交/快照标识、读取日期；有未提交改动要注明。没有版本信息就写缺口，不编哈希。

先识别入口、直接依赖和关键链路，再读对应源码；文档补充背景与历史。当前代码与历史方案冲突时先核对版本，不用当前实现否定历史实现。

先落范围与结构草稿，再逐模块读、写、核对；每闭合一条核心链路就更新还原稿，不等全仓及全部资料读完才产出。新增关联材料只有影响当前主张时才追，未展开部分明确列为边界，后续按需补齐。

本人范围采用用户确认；只有归属存疑或需要恢复改动过程时才查相关 Git/diff，不统计作者排名，也不用提交数量代替贡献。

## 2. 建立结构与契约

文件树覆盖所选模块的手写代码；普通样式、资源、生成代码可按目录合并，并注明省略原因。展开关键链路的文件和直接依赖，外部实现不可见就标边界。

以下是阅读检查项，不是要求每个机制输出六条 bullet。简单文件在树旁一句说明；复杂模块先解释职责和连接，再按真正影响还原的信息展开：

| 信息 | 记录粒度 |
|---|---|
| 职责与连接 | 负责什么、谁调用它、它依赖谁、关键导出符号 |
| 输入输出 | 真实参数/字段/类型、可空性、返回值与副作用 |
| 状态与契约 | 枚举真实取值、初始状态、状态真源、读写者、转换条件 |
| 实际行为 | 按执行顺序描述判断、更新、请求、回调、清理 |
| 分支与边界 | 成功、空值、失败、超时、重复操作、乱序、卸载；不适用的无需硬写 |
| 非显然细节 | 阈值及单位、白名单、生命周期、兼容分支、已知限制 |

关键事实可赋稳定 ID 或语义锚点。迁移旧稿保留 `F1` 等 ID 或列对应位置，但对照表写入维护记录，不放进技术实现概要正文。代码锚点只在模块标题、文件树或必要语句中自然出现，可加版本行号，但不能集中生成一节源码链接清单来替代正文。

## 3. 走通链路

至少记录一条主链路和有实际意义的异常链路：

`触发条件 → 文件/函数 → 输入 → 状态或副作用 → 下一跳 → 用户可见结果`

对异步逻辑写清先后次序、共享状态、检查发生的位置、清理时机。描述“防止了哪一次写入”，不笼统宣称“解决所有竞态”。没有实现的保护要照实保留，不替项目修代码。

至少对核心机制提供真实短片段或足以重写的伪代码。注明“源码节选”或“等价伪代码”及省略边界；伪代码保留判断顺序、常量单位和副作用，关键分支不能写“略”。未执行的片段不能称为可运行验证。无需复制整个仓库，也不要只有文件树和口头概括。

对后端字段缺失或异常，记录源码真实处理。不能添加默认文本、默认跳转或臆造的兜底；若源码原本有兜底，可客观记录其行为与问题。

测试用来发现作者意图和覆盖范围，必须与实现、契约交叉核对。写清“已有用例”“本次执行及结果”“仅静态推演”的区别。

## 4. 对齐证据

| 主张 | 可用依据 | 不能据此推断 |
|---|---|---|
| 某机制已实现 | 对应快照源码；旧档须检查版本、覆盖与冲突 | 本人完成、已发布、线上必然生效 |
| 本人做了什么 | 用户确认、任务记录、具体改动 | 文件全部由本人设计 |
| 历史决策或 Bug | 当时记录、用户明确回忆、相关变更 | 仅凭防御分支推断曾发生事故 |
| 上线与效果 | 发布/验收记录、观测数据及口径 | PRD 目标就是实测结果 |
| 方案与推演 | 方案原文、基于代码的分析 | 已做、已发生、当时已想到 |

找不到源码时保留“用户确认，代码待核验”，不编文件树，也不直接判定为 `设计意图`。方案里写“计划”只能确认存在意图，不能证明最终没实现。

指标保存来源、时间窗、样本/分母、基线和目标/报告值/本次实测属性。文档存在数字但口径缺失时保留原报告值，写明缺什么，不写“没有数据”。没数据就用交付范围或验证事实，不能造百分比；观察性差异不夸大为因果。

## 完成检查

还原稿已有版本范围、结构、契约、链路及关键复刻。每个缺口在交付说明或评估记录中写「缺什么 / 影响哪项主张 / 去哪里补」；技术实现概要正文只保留影响读者理解实现边界的局限，不把未知写成默认答案。版本与局部源码错误回填还原稿，个人责任或数字缺口回填母档。

若即将失去访问权限，优先保存用户获准留存的文件结构、关键行为、取值和边界。只读了一部分就明确覆盖范围，不称“完整还原”。资料量大不是逐一加工的理由，只沿目标链路展开。
