# 阶段 2：挖掘亮点

输入：还原稿与项目材料。输出：母档的主线、候选故事及个人边界，不生成重复实现清单。

## 1. 从事实选故事

优先选择岗位相关、本人参与深、能解释机制并有结果依据的内容；不按技术名词数量或代码行数排序。

| 类别 | 应回答的问题 |
|---|---|
| 交付价值 | 原先哪里不通？本人完成什么？现在具体支持什么？ |
| 技术难点 | 直觉做法为什么不够？冲突的约束或不确定性是什么？ |
| 工程亮点 | 哪个机制使正确性、复用、性能或排查能力更好？依据是什么？ |
| Bug 排查 | 什么信号触发排查？如何缩小范围、确定根因、验证修复？ |
| 成长与协作 | 哪次反馈、联调或判断改变了后续做法？个人动作是什么？ |

通常挑 2–3 个主故事，但这是上限参考而非配额。普通表单联调也有交付价值，不必包装成架构重构；没有真实事故就不生成事故故事。

## 2. 建立故事证据

写作前确认以下问题，正文用因果段落回答，不逐项复制成加粗卡片：

谁面临什么约束，本人明确负责哪部分？实际动作怎样改变链路？为什么这项选择有意义，代价是什么？结果由什么证明，还有什么没确认？

标题用具体问题或判断命名，避免“高可用体系”之类泛称。实现机制链接还原稿，不重复字段与函数表。状态和来源在故事旁短注一次即可，存在归属歧义时明确到动作，不能只在文末统一免责。

用 STAR(R) 检查：情境与目标、本人任务、动作和理由、结果与验证、反思都在。动作占主要篇幅。没有资料的格子不补造；未曾比较的备选标“现在回看”，不写成当时选型。

待优化项写「当前行为 → 触发风险的条件 → 改进机制与代价」，注明实际发生还是推演，以及是当时识别还是现在发现。历史原因不知道就写未知，不补成“工期紧”。

## 3. 处理真实 Bug

有旧 `B1` 等编号时保留；按真实因果展开：

`现象与触发条件 → 初始线索 → 假设与验证/排除过程 → 根因 → 修复 → 回归结果 → 遗留边界`

优先保存难以重现的条件、关键证据和排除错误方向的依据。没有排查过程记录就明确缺失，不能逆向编造日志、错误假设或定位耗时。

区分测试发现与线上事故、修复者与原代码作者。只在有依据时补流程根因、止损和防复发，不能把“没有提供监控材料”写成“团队没有监控”。

团队最终定位和修复可以写，但要点明谁做了什么。本人核对链接、复现或推动联调也有价值，不升级成独立定位。整改清单未勾选或缺落地证据时，只讲复盘建议，不能总结为“建成治理体系”。

## 完成检查

逐故事检查：是否有具体事实、本人动作、可解释的取舍、结果或明确缺口？是否把方案当实现、推演当事故、现在的理解当成当时的判断？

不成立的难点降级为普通交付，不删除其实现事实。缺证据的故事保留待核验，不能进入简历的确定性成果描述。
