# 技术实现概要结构参考

这是还原指定范围的技术档，不是复制整个仓库的承诺。标题使用项目名；按模块复杂度安排篇幅，不对每个文件重复统一表单。

## 范围与入口

先用一段话说明系统做什么，给出仓库、版本、读取日期与覆盖边界，再链接母档。依赖不可见、未读取部分与生成代码合并范围说明清楚。

## 文件树与职责

按真实文件生成带职责的树，手写业务代码覆盖到模块，普通样式、资源、生成产物可合并。树后解释依赖方向、状态所有者和外部契约。只有树不算还原。

## 全局运行链路

用短链路或必要的图说明入口、取数、状态、决策、视图、交互和清理如何连接。至少有一条正常链路及一条关键失败链路。详细版本和配置放在这里或末尾，不侵入母档的开头。

## 核心模块复刻

先写该模块的职责与调用关系，把文件路径和真实符号集中成锚点。随后用短段落说明机制，契约或状态值得比较时才列表格。

给出关键源码节选或等价伪代码，保留真实输入、状态作用域、判断顺序、输出和副作用。常量说明单位，省略外围代码需注明。代码展示之后用正常/异常输入走查，不能把伪代码重新复述成七条长 bullet。

复杂模块可以分到本地实现附录并互链；简单模块用职责和分支简表足够。若依赖不能还原，明确其输入输出边界，不以猜测补全。

## 剩余模块与局限

保存非面试亮点但还原必需的行为，例如频控、错误展示、跳转、埋点、卸载和默认值。区分源码已有兜底与建议做法，不替原实现修代码。只解释“减少了哪些更新”，不虚称“彻底没有竞态”。

## 不进入正文的维护信息

两份主文档都在**正文写完后直接结束**，不追加任何形式的收尾维护章节。以下内容不写进 `技术实现概要.md` 或 `母档.md`，改放交付说明、技能评估记录或任务回复：

- `来源与核验`、`旧事实覆盖迁移`、`缺口与验收` 这三类章节，以及换名后的等价物（`附录：来源`、`核验记录`、`验收与缺口`、`维护信息` 等）；
- 集中的源码锚点表——路径写在它解释的那个模块旁边，读者在读到某段实现时就能看到它出自哪里，比翻到文末查表有用；
- 旧事实 ID 对照、独立验收过程、缺口矩阵、评估报告链接。

判断方法：这段内容是帮读者**理解这个系统**，还是帮维护者**追溯这份文档怎么写出来的**？后者不属于正文。读者要的是实现，不是文档的施工记录。

版本、读取范围、明确不覆盖的部分写在开头的范围说明里，一次交代清楚；影响某条主张的证据边界，就近写在那条主张旁边一句话。这样边界信息出现在读者需要它的位置，而不是堆在末尾。

读者需要回到源码猜关键状态或条件时，应补强对应模块正文或实现附录，而不是用末尾核验表弥补。
