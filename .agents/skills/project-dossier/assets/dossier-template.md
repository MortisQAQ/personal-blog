# 母档结构参考

母档回答七个问题，按固定顺序组织。这是章节目的说明，不是逐格填写的表单：标题用项目自己的话，写作提示删掉，篇幅由重要性决定。

七个章节都要有。确实无内容的（如没有真实事故），写明"无"及原因，不留空标题，也不用推演填充。

## 开头：先让人知道值得读什么

项目名下用短段落交代服务谁、改变哪条业务链路；紧接着说明本人负责和不负责什么、最值得讲的判断、结果证据的边界。读者不应先经过版本、文件路径和技术栈长表。

附一行导航指向下方核心章节与技术实现概要。需要版本时一行注明，快照详情在技术实现概要。

## 1. 背景与目标

从用户或业务的问题讲起，再解释为什么需要这次交付。把业务目标和技术约束连接起来，不泛讲行业背景，不把目标当成结果。

写清这次交付要改变什么、成功长什么样。目标是当时定的目标，不是事后知道的结果。

## 2. 个人职责和边界

用一条简明链路解释上游输入、本人所在模块和下游结果。读者应理解责任与状态归属，而不是背内部系统名。

明确三件事：我做了什么、我没做什么、哪些是团队机制或既有基建。当前页面有的功能，不等于本人全都写过。平台侧能力是接入还是搭建，必须分清。

## 3. 最难的问题

选一到三个真正的难题，围绕具体难题起标题。难在哪要具体：是约束冲突、信息不足、跨系统耦合，还是现象与根因距离远。

每个难题先解释约束冲突，再写实际动作、机制和选择，最后给结果与代价。用段落表达因果，不靠列表堆砌。实现细节链接技术实现概要，不在此复写字段表。

以 STAR(R) 自查完整性，不把 S/T/A/R 做成重复加粗项。排查类难题必须保留线索、定位依据和回归方式，缺失的排查过程不能补造。

## 4. 关键技术决策及备选方案

与第 3 章的区别：第 3 章讲问题怎么解决，本章讲为什么选这条路而不是别的。有独立判断价值的决策才单列，否则并入第 3 章。

每个决策给：约束条件、候选方案、选择理由、放弃理由、代价。被否决的方案往往比选中的更能说明约束——写清它错在哪，而不只是"不合适"。

真有可比维度时才用表；两三个方案的对比适合表格，单一方案的取舍用段落。没有历史选型记录时，备选方案标注为"现在回看"，不伪装成当时的正式评估。

## 5. 结果与证据

优先讲已经确认的交付与验证。区分四种不同主张：代码存在、本人完成、已上线、有效果。

确有多组数字才使用结果表，表中标清是目标值、文档报告值还是本次实测值，以及时间窗、分母和限制。两组非随机分流的对比只能表述为相关性。没有数字不减分，虚构因果不允许。

同时写清验证手段的真实覆盖：跑了什么、没跑什么、哪些路径没有自动化覆盖。

## 6. 失败、复盘和后续改进

讲清真实失误、本人承担的部分、哪些认识改变了、后续哪些已做哪些没做。

现在发现的问题单独标注，不逆向虚构当时的诊断或成长。改进项区分"已落地"与"已识别未落地"，后者说明为什么没做（排期、跨团队、风险），不含糊带过。

没有真实事故时不强行生成本章，改写认知变化或方法沉淀，并说明无事故。

## 7. 可能被追问的问题

围绕主故事给"实现 → 决策 → 验证和边界"的连续三层追问，每问给可开口的短回答要点与技术实现概要锚点。

仅保留关键链，完整题库按需派生到面试套件。追问要能真正问住人，不是自问自答的软球；答案要给边界，不是"详见某章"。

## 结尾

用一小段集中记录影响可投递性的缺口、来源摘要和最近更新。缺口不能成为前面夸大主张的免责条款。
